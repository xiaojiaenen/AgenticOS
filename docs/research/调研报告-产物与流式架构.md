## 一、产物目录与版本机制

### 1.1 目录结构:按"用户 × 会话 × 版本"隔离

产物统一落在 `data/` 下,命名规则 `u{user_id}_s{session_id}_v{version}`:

- **网站**:`data/websites/u1_s1790860478302-77kw06_v1/`(内含 `index.html` / `css/` / `js/` / `dist/` / `node_modules/`)
- **PPT**:`data/ppt-sessions/u{user}_s{session}_v{n}/`(内含 `slide_*.svg`)

`backend/app/core/data_path.py:127-154` 提供两个函数:`_parse_dir_name()` 解析、`next_version_dir()` 取"同用户同会话的最大版本 +1"。**首次生成时创建 v1,同会话再次生成走 v2、v3……** 目录互不覆盖,天然带历史。

### 1.2 迭代行为:原地改,不产生新版本

这是当前实现最需要注意的一点 —— **版本目录只在"首次生成"时用,后续迭代是原地覆盖**:

| 产物 | 迭代机制 | 结果 |
|---|---|---|
| PPT | `_get_edit_hint()`(`artifacts.py:236-275`)在下一轮对话注入提示:"当前对话已有 PPT《X》(N 页),用 read_slide(N) 读取后 save_slide 覆盖修改的页",并列出已有页码 | 覆盖同一目录的 `slide_N.svg`,**不新建 v2 目录** |
| 网站 | 首轮 `copy_template("vanilla")` 建项目目录,后续 `build_website` 在**同一项目目录**内迭代源码再构建 | 原地改 + 重新 build,**不新建 v2 目录** |

**结论**:v2/v3 目录目前只在"同一会话里又完整重新生成一次(而非迭代)"时才会产生。**没有版本列表 API**(openapi 里只有 `/website/deploy/project/{slug}` 查部署记录,无列版本接口),所以用户目前无法查看历史版本。

### 1.3 多技术栈预览:React/Vue 可正常预览

模板目录 `data/website-templates/` 实际有 **react / vue / vanilla 三套**。预览走 `ArtifactFactory._inline_dist_assets()`(`artifacts.py:100+`):把 `dist/index.html` 里的 `<link rel=stylesheet href=/assets/x.css>` 和 `<script src=/assets/x.js>` 读取后**内联**成自包含 HTML,再塞进 `srcdoc` 预览。

因为三套模板都由 Vite 构建、产物结构相同(`dist/index.html` + `assets/`),**React/Vue 项目同样能预览**。限制:若项目用了路由懒加载 / 动态 import,运行时按需加载的额外 chunk 在内联后路径会失效(需二次改造 `_inline_dist_assets` 才能支持)。

### 1.4 部署与审批:链路完整可用(已实测)

- 网站:发起 `POST /website/deploy` → `status=pending` → admin 在 `GET /admin/website/deploys` 看到 → `POST /admin/website/deploys/{id}/decision`(body 用 `status` 字段)→ `status=deployed` + 分配 `deploy_url`。**本轮测试全链路走通**。
- 部署产物可访问:生产 nginx `try_files $uri $uri/` 支持目录 URL;本地 dev 已修(`StaticFiles(html=True)`,实测 `/sites/{slug}/` 直开)。

### 1.5 关于"方便查看历史版本"——建议(尚未实现)

当前无版本 API、无版本 UI。若要做,最小方案:

1. 后端加 `GET /agent/sessions/{id}/versions`(扫 `data/websites|u{sid}_*` 与 `ppt-sessions/u*_s{sid}_*`,返回版本号、时间、产物名);
2. 产物面板顶部加一个版本下拉,选中即调 `/sessions/{id}/artifacts?version=n` 加载;
3. 配套把"迭代改为写新版本目录"(PPT:save_slide 写 v(n+1);网站:build 前 copy 一份),否则版本号没有实际内容可回溯。

## 二、流式渲染架构:为什么"感觉像单轮"

### 2.1 结论先行:后端是标准 ReAct 多轮,单轮感是前端渲染丢信息造成的

- **多轮是真的**:`factory.py:105` `while step_count < max_steps`(默认 `agent_max_steps=10`),流程 = LLM → 有 tool_calls 就执行并 `add_tool_message` 回喂 → `step_count += 1` → **再次调 LLM**,直到无工具调用才 `done`。
- **顺序信息在源头免费可得**:`factory.py` 内部每个事件都带 `step` 和 `run_id`(`_build_event(..., step=step_count)`)。
- **丢失点**:后端 `orchestrator.py:_map_agent_event()` 的 6 个分支(delta / reasoning_delta / tool_calls / tool_results / tool_error / done)**没有把 `event.step` 复制进 SSE payload**;前端 `useChatStream.ts` 再把 delta / reasoning / toolCalls **折叠进三个独立"桶"**(`message.text` / `reasoningText` / `toolCalls[]`)。两个桶之间的时间关系没有字段承载,于是渲染层只能把"工具链调用历史"和"思考过程"各自做成固定位置的折叠块 —— 视觉上就变成"一段话 + 一坨工具",自然像单轮。

### 2.2 顺带发现的两个既有缺陷

1. **流式态与刷新态不一致**:流式中整个多轮被合并成一条 assistant 消息;刷新后 `agentService.ts:617-645` 按原始消息逐条还原,一次多轮运行会**裂成多个气泡**。
2. **刷新后推理内容消失**:加载历史时没有恢复 `reasoningText`,尽管后端 `session_storage.py` 存了 `reasoning_content`。

### 2.3 改造成本评估

**A 档(纯前端,2-3 人日)**:给 `Message` 加有序 `blocks[]`(`reasoning`/`text`/`tool`),`useChatStream` 按事件到达顺序 append 而非折叠;`ChatMessage` 把固定三块换成 map。**只改善流式播放期间的观感,刷新后退化**(历史加载会重新拍平)。需重做搜索高亮(依赖 `message.text` 单字段)。

**B 档(后端补 seq + 持久化,5-8 人日)**:
- 后端很轻:`_map_agent_event` 补 `seq`(单调递增)/`step`(直接取 `event.step`)/`ts`,单函数 6 分支的机械改动,约 0.5-1 人日;
- 大头在前端:按 seq 重建 block 列表、流式/历史统一渲染路径、持久化兼容、搜索高亮重做、回归测试;
- **附带修掉上面两个既有缺陷**。

**第三方库不划算**:streamdown 只解决 markdown 抖动;Vercel AI SDK 要重写整个 SSE + 审批链路,成本远高于自研。现有 motion + react-markdown 足够。

**推荐**:先 A 档验证交互形态(工具卡片插在正文中间的手感、审批面板锚点),再投 B 档。**注意顺序**:B 档落地前不要动历史加载的"多轮合并",那目前是步骤边界唯一的存活载体。

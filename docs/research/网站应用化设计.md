# 网站应用化设计（Manifest / 数据 / 权限 / 审批）

> 状态：**设计文档，暂不实现**。
> 本文描述用户生成的网站如何演进成"有登录、有权限、能连数据库"的
> 应用形态，以及配套的接口、SDK、审批流与迁移路径。
>
> 背景：当前 AgenticOS 的网站发布是**静态站点**模型 —— 用户在会话里让
> AI 生成代码，构建产物（`dist/`）拷贝到 nginx 静态目录，公开的走
> `/sites/<slug>/`，私密的走带签名的后端端点。整条链路没有服务端运行时，
> 因此网站**天然无状态、无账号、无数据**。
>
> 用户提出的诉求：生成的网站可能需要登录、权限，或读写数据；希望有
> 接口/SDK，管理员可审核授权范围。

---

## 0. 先说结论（方案取舍）

| 维度 | 方案 A：静态站点 + 外部 API | 方案 B：应用运行时（本文） |
|------|------------------------|------------------------|
| 用户改动量 | 零（网站代码自己调外部 API） | 需要在 manifest 里声明数据模型 |
| 平台掌控力 | 弱（数据在第三方，平台只管页面） | 强（数据、权限、审计都在平台内） |
| 越权风险 | 由用户自己承担（key 泄露即数据泄露） | 平台可按申请范围限权 |
| 审核成本 | 低（只看代码） | 中（要审 manifest + 权限申请） |
| 实施成本 | 几乎为零 | 大（需要运行时、鉴权、数据层） |

**建议：分两步走。**

- **第一步（低成本，先落地）**：把「应用能力」抽成**平台侧托管服务**——
  数据存储、鉴权、文件、通知，由 AgenticOS 提供 HTTP API 与 SDK；
  用户的静态网站通过 SDK 调用这些 API。网站仍然是静态的，但已经能登录、
  能存数据、能按角色授权。**这解决了 80% 的诉求，实施成本约等于方案 A。**
- **第二步（按需再做）**：确有需要的服务端逻辑（定时任务、webhook、
  服务端密钥）再引入应用运行时。

本文以**第一步**为主体展开，第二步只在末尾给出演进路径。

## 1. 术语与边界

| 名称 | 含义 |
|------|------|
| **应用（App）** | 一个已发布的网站 + 一组数据模型 + 一份权限声明 |
| **Manifest** | 应用的声明文件（JSON）：数据模型、权限、页面路由 |
| **数据模型（Model）** | 应用内的一张表，平台托管存储 |
| **数据集（Dataset）** | 一组模型的集合，对应一个"应用环境" |
| **主体（Principal）** | 访问数据的人或服务：终端用户、应用自身、平台管理员 |

**明确不做的**（第一步范围外）：

- 用户自定义服务端代码（Node/Python 函数）——那才是真正的运行时，
  带来代码执行安全、依赖管理、冷启动等一整片问题；
- 应用间跨库 JOIN；
- 离线同步 / 复杂事务。

## 2. Manifest 规范

放在发布产物根目录，文件名固定 `agenticos.app.json`：

```jsonc
{
  "$schema": "https://agenticos.local/schemas/app-manifest.v1.json",
  "version": 1,

  // ── 展示信息 ──
  "name": "客户反馈看板",
  "description": "收集客户反馈并按状态汇总",
  "icon": "📊",

  // ── 认证方式 ──
  // none    = 公开只读（当前静态站点等价物）
  // builtin = 平台托管账号（邮箱 + 密码 / SSO 转发）
  // oauth   = 外部 IdP（企业微信 / LDAP / OIDC）
  "auth": {
    "mode": "builtin",
    "loginPath": "/login",
    "allowSignup": false,
    "roles": ["viewer", "editor", "admin"]
  },

  // ── 数据模型 ──
  "models": [
    {
      "name": "feedback",
      "fields": [
        { "name": "title",   "type": "string", "required": true },
        { "name": "body",    "type": "text" },
        { "name": "status",  "type": "enum",
          "options": ["new", "processing", "done"], "default": "new" },
        { "name": "rating",  "type": "number" },
        { "name": "ownerId","type": "string", "ref": "user" }
      ],
      // 谁可以读 / 写 / 改 / 删
      "permissions": {
        "read":   ["owner", "role:admin", "role:editor"],
        "create": ["role:viewer", "role:editor", "role:admin"],
        "update": ["owner", "role:editor", "role:admin"],
        "delete": ["role:admin"]
      }
    }
  ],

  // ── 平台能力申请（全部要管理员审批）──
  "capabilities": {
    "storage":   { "mode": "platform" },   // 数据存平台
    "files":     { "maxSizeMb": 10 },
    "outbound":  {                          // 允许访问的外部域名白名单
      "allow": ["api.example.com"],
      "mode": "deny"                        // 默认拒绝
    },
    "email":     { "templates": ["notify-owner"] }
  },

  // ── 页面 ──
  "routes": [
    { "path": "/",        "entry": "index.html" },
    { "path": "/login",   "entry": "login.html" },
    { "path": "/admin",   "entry": "admin.html", "requiresRole": "admin" }
  ]
}
```

### 2.1 设计要点

- **Manifest 是声明，不是代码**。平台按声明生成 API 与权限校验，
  用户代码只负责调 SDK。这是"平台掌控力"的核心来源。
- **能力申请默认拒绝**（`outbound.mode = "deny"`）。静态站点今天能任意
  fetch 外部域名 —— 换成应用形态后这是最主要的滥用面，必须显式申请。
- **`ref` 字段做引用完整性**：模型间引用（如 `ownerId → user`）由平台
  在写入时校验，避免脏数据。
- **manifest 版本化**（`version`）。将来加字段只升版本，老 manifest
  继续按 v1 语义解释。

## 3. 平台托管 API

所有应用的数据访问走**同一组端点**，鉴权用应用级 token：

```
POST   /api/v1/apps/{app_id}/auth/login        → 换取 access token
POST   /api/v1/apps/{app_id}/auth/signup       → （allowSignup 时）
GET    /api/v1/apps/{app_id}/me                → 当前主体 + 角色

GET    /api/v1/apps/{app_id}/data/{model}      → 列表（带过滤/分页）
POST   /api/v1/apps/{app_id}/data/{model}      → 新建
GET    /api/v1/apps/{app_id}/data/{model}/{id}
PATCH  /api/v1/apps/{app_id}/data/{model}/{id}
DELETE /api/v1/apps/{app_id}/data/{model}/{id}

POST   /api/v1/apps/{app_id}/files             → 上传（返回受权 URL）
GET    /api/v1/apps/{app_id}/files/{file_id}
```

### 3.1 鉴权模型

- **终端用户 token**：由 `POST /auth/login` 换取，payload 含
  `{ app_id, user_id, roles, exp }`，签名用平台密钥。默认 24h。
- **应用 token**：服务端调用（用户在自己的后端调平台 API 时用）。
  由 `api_keys` 体系扩展而来，带 `app_id` 作用域。
- **平台管理员**：任何 app 端点都接受管理员身份（审计与救场）。

**关键点**：权限判定只发生在平台端。用户代码里的 `if (user.isAdmin)`
只是 UI 表现，不是安全边界 —— 数据接口会再判一次。

### 3.2 行级权限

`permissions` 字段里的 `owner` 语义：**记录归属者等于当前用户**。
即：

```
can(user, "feedback", "update", record) =
    record.ownerId == user.id  OR  user.roles ∩ {editor, admin} ≠ ∅
```

平台在查询层直接注入条件，不依赖用户代码过滤。

## 4. 前端 SDK

给生成的网站代码用的浏览器 SDK（也可用于 Node 侧）：

```js
// 注入到页面的全局：window.AgenticOS
const { auth, data, files } = window.AgenticOS;

// 登录
await auth.login({ email: 'a@b.com', password: '…' });
const me = await auth.me();          // { id, email, roles: ['editor'] }

// 数据（CRUD 走平台，权限由平台判）
const list = await data.feedback.list({
  where: { status: 'new' },
  order: { createdAt: 'desc' },
  limit: 20,
});
await data.feedback.create({ title: '卡顿', body: '…', status: 'new' });
await data.feedback.update(id, { status: 'done' });

// 文件
const up = await files.upload(fileBlob);
```

SDK 特点：

- **零配置**：页面里 `<script src="/sdk/agenticos.js">` 即可，
  不需要写 key（token 走 HttpOnly cookie 或内存）。
- **薄**：不做本地缓存、不做离线队列 —— 那些是应用自己的事，
  SDK 只保证"请求经过平台鉴权"。
- **体积目标 < 20KB gzip**。

### 4.1 与 AI 提示词的衔接

AI 生成网站时，提示词里注入当前 manifest 的能力摘要：

```
本应用可使用平台托管能力（通过 window.AgenticOS）：
- 数据模型：feedback（title: string 必填, body: text, status: enum[new|processing|done]）
- 权限：read=[owner,role:admin,role:editor]，create=[…]
请不要把 API key 写进前端代码；认证由 SDK 负责。
```

## 5. 权限与审批流

### 5.1 管理员审核什么

发布申请时，manifest 与普通网站**分开审**：

| 审核项 | 依据 | 风险级别 |
|--------|------|---------|
| 数据模型是否合理 | manifest.models | 低 |
| 权限声明是否过宽 | manifest.models[].permissions | **中** |
| 外部域名白名单 | manifest.capabilities.outbound.allow | **高** |
| 认证方式 | manifest.auth | 中 |
| 代码本身 | 既有源码扫描 + AI 评审 | 中 |

**过宽的权限要能一眼看出来**。例如 `read: ["*"]` + `create: ["*"]` +
`outbound.allow: ["*"]` 组合 = 开放代理，必须人工细看。

### 5.2 状态机

```
draft ──申请发布──▶ pending ──批准──▶ deploying ──▶ deployed
                       │                              │
                       └──拒绝──▶ rejected            │取消
                                                       ▼
                                                    cancelled
                                                       │
                                          重新提交（新版本）
                                                       ▼
                                                  superseded
```

与现有 `website_deploys` 的状态机一致（已有 `pending/approved/deployed/
rejected/cancelled/superseded/failed`），可直接复用同一套审批队列 UI。

### 5.3 权限收敛

批准时允许管理员**收紧** manifest 的权限声明（例如去掉
`outbound.allow` 的某几个域名）。收紧后的版本才是实际生效的版本 ——
"申请什么"与"批什么"分离，避免用户改一版就多要一点权限。

## 6. 数据存储

### 6.1 表结构

一张通用表 + JSON 列 vs 每应用一张物理表？

**建议：每应用一张物理表**（`app_data_<app_id>_<model>`）。

- 通用 JSON 表在查询、索引、约束上处处别扭；
- 物理表可以按 manifest 生成真实列（类型、必填、枚举约束），
  数据库层面就有约束，不靠应用代码；
- 迁移成本可接受：应用数量是几百量级，不是百万量级。

用户 UUID 统一用 `gen_random_uuid()`（PostgreSQL）/ `UUID()`（MySQL 8）。

### 6.2 存储引擎

**第一步建议 PostgreSQL**，理由：

- JSONB + GIN 索引（半结构化列的过滤）；
- 行级安全（RLS）可以作为第二道防线，与 manifest 权限叠加；
- `uuid` 类型原生。

若必须沿用 MySQL，则退化为 `JSON` 列 + 应用层过滤，权限判定的复杂度不变。

### 6.3 行级安全的双保险

平台在 API 层判权限已经够用；但如果用 PostgreSQL，可以额外用 RLS
把 manifest 的 `owner` 规则下推到数据库：

```sql
ALTER TABLE app_data_7_feedback ENABLE ROW LEVEL SECURITY;
CREATE POLICY feedback_read ON app_data_7_feedback
  USING (
    owner_id = current_setting('appic.user_id', true)::uuid
    OR current_setting('appic.roles', true) LIKE ANY (ARRAY['%editor%','%admin%'])
  );
```

这不是必须的（应用层判已经正确），但能在"应用层代码出 bug"时兜底。

## 7. 用户故事 → 设计映射

| 用户说 | 落到哪 |
|--------|-------|
| "网站需要登录" | `auth.mode = builtin` + `/auth/login` + SDK `auth.login` |
| "不同角色看到不同数据" | `models[].permissions` 的 role 规则 + 行级过滤 |
| "只读数据" | `permissions` 里不给 create/update/delete |
| "可增删改数据" | 显式列 create/update/delete + `owner` 归属规则 |
| "管理员申请可审核" | 审批队列审 manifest 的权限声明 + 外部域名白名单 |
| "要能接数据库" | 第一步是平台托管存储；接外部数据库属于"能力申请"，管理员批准后才允许 |

## 8. 实施路线（建议分三步）

### 步骤 1：数据与鉴权底座（不动发布链路）

1. `apps` / `app_users` / `app_roles` 三张表；
2. `POST /auth/login` 签发应用级 token（复用 `create_access_token`，加 `app_id` scope）；
3. `app_data_<app_id>_<model>` 动态建表（由 manifest 生成 DDL）；
4. CRUD 端点 + 行级权限判定。

**这一步完成后，静态网站就能"登录 + 存数据"** —— 因为 SDK 是纯前端 JS，
静态站点不用改部署方式。

### 步骤 2：Manifest + 审批

1. manifest schema 与解析器；
2. 发布流程里识别 `agenticos.app.json`，走独立审核队列；
3. 审批 UI 增加"权限审阅"分区（比现有源码扫描更结构化）；
4. 批准时把收紧后的 manifest 落库。

### 步骤 3：运行时（按需，可能永远不做）

只有在出现"必须有服务端逻辑"的真实需求时才做：

- 用户函数托管（受限运行时，无网络或受限网络、CPU/时长限额）；
- 定时任务（cron）；
- webhook 入站。

## 9. 安全清单（实现时逐条对照）

- [ ] 所有 app 端点校验 token 的 `app_id` 与路径一致（防跨应用越权）
- [ ] 所有 app 端点校验 token 未过期、未吊销
- [ ] 行级权限在**查询层**注入，不依赖用户代码
- [ ] 出站域名白名单在**平台代理层**强制（不是 SDK 层）
- [ ] 上传文件做类型与大小校验，存储路径不可遍历
- [ ] 审计日志记录：谁（主体）、对什么（模型）、做了什么（CRUD）、结果
- [ ] 管理员可导出/删除应用数据（合规要求）
- [ ] 应用删除时物理清理表与文件（不留孤儿）
- [ ] 令牌不写日志

## 10. 与现有系统的关系

| 现有 | 复用 |
|------|------|
| `website_deploys` 审批队列 | 直接复用（新增 manifest 审核项） |
| `api_keys` | 应用 token 的作用域扩展 |
| `auth_sessions` / JWT | token 签发与校验 |
| `agent_run_traces` 审计 | 审计日志的字段与风格 |
| 作品库 `/s/{code}/` | 应用入口与短链不变 |
| `website_review_service` 的源码扫描 | 应用审核的第一道关 |

**不需要改的**：网站生成链路、AI 提示词主体、构建与 nginx 发布、
作品库卡片、短链 —— 这些在"应用形态"下都保持不变，只是多了一个可选的
manifest 与一组可选的平台 API。

## 11. 未决问题

1. **终端用户身份从哪来**？平台账号体系是给"使用 AgenticOS 的人"的；
   网站的终端用户往往是外部客户。是复用平台账号体系（那外部客户也得
   注册平台账号）还是引入独立的应用用户表？倾向后者。
2. **配额与计费**：外部终端用户的写操作要不要计入平台成本？
3. **跨应用共享数据**：暂时不做，但如果出现"看板要从另一个应用取数"
   的需求，需要设计"应用间授权"而不是让用户直连数据库。
4. **隐私合规**：终端用户数据算谁的？删除应用时是否需要通知外部用户？

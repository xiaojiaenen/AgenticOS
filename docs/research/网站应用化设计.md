# 网站应用化设计（Manifest / 数据 / 权限 / 审批）

> **实施状态（2026-11-25）：步骤 1+2 已实施**（manifest 声明、plan 审批、数据托管；
> 后端 `app_platform` 服务 + 前端「网站应用」面板）。下方「暂不实现」为原始状态档案。

> 状态：**设计文档，暂不实现**（v2 优化于 2026-11-17，加入竞品与开源调研结论）。
> 本文描述用户生成的网站如何演进成"有登录、有权限、能连数据库"的应用形态，
> 以及配套的接口、SDK、审批流与迁移路径。
>
> 背景：当前 AgenticOS 的网站发布是**静态站点**模型 —— 用户在会话里让
> AI 生成代码，构建产物（`dist/`）拷贝到 nginx 静态目录，公开的走
> `/sites/<slug>/`，私密的走带签名的后端端点。整条链路没有服务端运行时，
> 因此网站**天然无状态、无账号、无数据**。
>
> 用户诉求：生成的网站可能需要登录、权限，或读写数据；希望有接口/SDK，
> 管理员可审核授权范围。

## 0. 结论与本次优化摘要

**分两步走的总策略不变**：第一步做平台侧托管能力（静态网站 + SDK 调平台 API），
解决 80% 诉求；第二步按需引入服务端运行时。

本次基于调研对原方案做了 6 处实质优化：

| # | 原方案 | 优化后 | 依据 |
|---|--------|--------|------|
| 1 | 用户/AI 手写 JSON manifest（含字段定义） | **AI 从业务描述自动生成 manifest 草稿**，先出需求文档再出声明，用户对话确认 | 秒哒"业务描述替代数据库设计"、先 PRD 后开发 |
| 2 | 每应用一张物理表 `app_data_<app_id>_<model>` | **共享表 + `app_id` 列 + JSONB + RLS 为主档**；schema/独立库隔离作企业级选项 | Supabase/业界多租户共识：物理表与 schema 都会 fan-out，RLS 是标准 |
| 3 | 无环境概念 | 增加 **dev/prod 双环境隔离** | 秒哒 3.5 / 企业版"数据库多环境隔离" |
| 4 | 明确"不做实时" | 实时订阅降为**第二步可选能力**（平台已有 SSE 基础设施） | 秒哒把实时协同列为核心三模块之一 |
| 5 | 审批只审 manifest 快照 | 改为审 **plan 变更计划**（create/update/drop/skip），批准即 apply，幂等可重放 | SimpleBase `dev plan` / `dev apply` 模型 |
| 6 | 终端用户身份问题列为未决 | **定论：独立 `app_users` + membership 表**，租户归属从 membership 查，不读 JWT claim | Supabase 多租户指南：JWT 过期会导致已移除用户仍越权 |

## 0.5 对标调研（2026-11-17）

### 秒哒（百度，最直接的生产级对标）

秒哒是国内"对话式全栈应用生成"的标杆，其后端能力结构与本方案高度同源：

- **后端三模块**：数据库表 / 登录权限 / 实时协同。与本方案的"数据 / 鉴权 / SDK"几乎一一对应，
  **验证了第一步方向的正确性**。
- **自动生成**：识别业务对象（订单、用户、商品）自动建表含字段与关系；涉及用户体系时
  自动生成登录（邮箱/手机/验证码/微信），用户数据与业务数据通过 userID 自动关联
  —— 对应本方案的 `ownerId` 归属规则。
- **关键方法论**：官方文档明确"**通过业务描述替代数据库设计**"，推荐说
  "用户可以发布旅行计划并允许其他用户评论"，不推荐"创建含 title/content 字段的表"；
  且所有项目**先产出产品需求文档再进入开发**。→ 这是对原方案 manifest 生成方式最直接的修正依据。
- **3.5 / 企业版**（2026）：多应用共享后端、数据库多环境隔离、后端资源分级；
  企业-团队-成员三级权限、多团队资源隔离、测试/生产环境隔离。
  → 印证"共享后端 + 逻辑隔离 + 环境隔离"是规模化路线，而非每应用独立库。
- **生态**：300+ 场景模板、插件市场（百度搜索/地图）、数据中台 API 编排对接 MySQL/MongoDB。

### 美团 NoCode（轻量路线的参照）

- 自然语言 + 可视化组件生成 Web 应用/轻应用/业务工具/活动页面，**10 秒级生成**、免费算力、
  明确"不设商业化路径"（公开灰测阶段）。
- 定位是零成本体验与前端快速验证，并未强调后端数据能力。
- → 说明"**纯静态 + 轻量**"本身是一条成立的产品路线，本方案第一步（静态网站也能存数据）
  是在不破坏该体验的前提下加能力，应保持 SDK 零配置与轻量。

### 海外 AI 应用生成器（Lovable / Bolt / v0，2026-11-17 补）

这一轮补查了鉴权/权限的业界做法，三家正好覆盖三种路线：

| 产品 | 后端/鉴权做法 | 可借鉴点 |
|------|--------------|----------|
| **Lovable** | 原生集成 Supabase。一句"加登录"自动建用户表、配 RLS、生成登录/注册/登出页；Supabase 官网称其"支撑数百万个 AI 生成应用" | **自动生成鉴权**（建表 + RLS + 登录 UI 一步到位），对应本方案 manifest 生成后自动出数据/权限配置 |
| **Bolt.new V2**（Bolt Cloud，2025） | 每个项目自动配好登录（邮箱/密码、验证、泄露密码检测）+ 无限 Supabase 数据库 + 存储 + 分析；2026-04 起原生支付 | 平台**预置可用后端**，不用创作者自己接账号/配密钥 —— 对应本方案"平台托管 API"的零配置体验 |
| **v0**（Vercel） | 偏前端 + Next.js 沙箱，UI 质量最好；登录/Supabase 需手动接 | 反例参照：不承担后端时，鉴权体验会打折 —— 印证本方案要把鉴权做进平台底座 |

**三条共识**（三家 + Supabase 官方 + 多份安全复盘一致）：

1. **两把钥匙 + 用户令牌**：公开的客户端钥匙可进前端，但只认应用不认人；真正的权限靠用户令牌 + 数据库 RLS 判定。这是事实标准，与本方案 3.1 完全同源。
2. **鉴权必须自动生成**：让 AI/平台从业务描述自动建表、自动配 RLS，而不是让创作者手写策略 —— 手写必错（见第 9 节踩坑）。
3. **安全不是生成完再补**：Auth/RLS/密钥的最常见漏洞都出在脚手架默认值上，要作为平台默认值和 CI 关卡固化（见第 9 节）。

### 开源方案

| 项目 | 可借鉴点 | 与本方案的关系 |
|------|----------|----------------|
| **SimpleBase**（github.com/linkxzhou/SimpleBase） | 单二进制起一套后端；SQL/集合/KV/对象存储/定时任务/触发器/实时订阅/LLM 网关；`simplebase.json` 声明式 + `dev plan`（只读列出 create/update/skip）+ `dev apply`（先查后写、幂等重复 skip、远端必须 `--yes`）；Scoped Key、SQL 守卫、日志脱敏 | **plan/apply 幂等模型**直接可用于审批流；"按模块分助手、只读助手拿不到写权限"可借鉴到 AI 生成阶段的权限约束 |
| **Supabase（多租户模式）** | 共享 schema + `tenant_id` + RLS 是"现代标准"；租户归属放 membership 表而非 JWT；视图需 `security_invoker=true` 否则绕过 RLS；helper 函数放非暴露 schema + 空 `search_path` | 纠正本方案第 6 节的隔离决策（详见 6.1）；`current_setting` + policy 的正确写法见 6.3 |
| **JarvisHub** | Canvas State + Protocol Bridge + Agent Runtime 三层；capability manifest + mutation validation + execution grant | "门卫"思想：能力校验统一收口到平台代理层，而非散落在 SDK |
| 选型避坑 | Dify / FastGPT 的 Apache 2.0 带附加条款（多租户需额外授权、不得移除品牌）；n8n 为 Sustainable Use License 限制商用 | 若后续引入开源组件，先读 LICENSE，别信 README 里的 "open source" |

### 调研带来的三条判断

1. **方向被验证**：托管后端 + 声明式数据 + 自动生成鉴权，是秒哒、Supabase、SimpleBase 的共同选择。
2. **两处要改**：manifest 不该让人手写（应从业务描述生成）；每应用物理表不是最优（共享表 + RLS 才是可扩展档）。
3. **两项要补**：环境隔离（dev/prod）与 plan/apply 幂等审批，是"生产级"与"Demo"的分水岭。

## 1. 术语与边界

| 名称 | 含义 |
|------|------|
| **应用（App）** | 一个已发布的网站 + 一组数据模型 + 一份权限声明 |
| **Manifest** | 应用的声明文件（JSON）：数据模型、权限、页面路由 |
| **数据模型（Model）** | 应用内的一类业务数据，平台托管存储 |
| **环境（Env）** | 同一应用的 `dev` / `prod` 两套隔离数据（秒哒企业版同款） |
| **主体（Principal）** | 访问数据的人或服务：终端用户、应用自身、平台管理员 |

**明确不做的**（第一步范围外）：

- 用户自定义服务端代码（Node/Python 函数）—— 真正的运行时，带来代码执行安全、
  依赖管理、冷启动等一整片问题；
- 应用间跨库 JOIN；
- 离线同步 / 复杂事务；
- 实时协同（第二步可选，见 3.3）。

## 2. Manifest 规范

### 2.0 Manifest 从哪来（本次新增，关键）

**不让用户手写 JSON**。生成链路改为：

```
用户一句话需求
   │  ① AI 先产出"产品需求文档"（用户确认/修正）
   ▼
需求文档（谁产生数据、谁查看、是否需登录）
   │  ② AI 按 manifest schema 生成草稿（字段/权限/能力申请）
   ▼
manifest 草稿 ──▶ 对话中确认 ──▶ 随代码一起构建 ──▶ 管理员审批
```

- AI 生成时拿到的是**业务描述**，产出的是**结构化声明**，与秒哒"业务描述替代数据库设计"一致。
- manifest 必须过 **JSON Schema 校验**（机器可判），校验不过不进入审批队列。
- 用户在对话里改的是"可见的业务语言"（如"评论只有作者能删"），AI 翻译成对应的
  `permissions.delete: ["owner"]`，避免用户直接面对字段级 JSON。

放在发布产物根目录，文件名固定 `agenticos.app.json`：

```jsonc
{
  "$schema": "https://agenticos.local/schemas/app-manifest.v1.json",
  "version": 1,

  // ── 展示信息 ──
  "name": "客户反馈看板",
  "description": "收集客户反馈并按状态汇总",
  "icon": "📊",

  // ── 认证方式 ──
  // none    = 公开只读（当前静态站点等价物）
  // builtin = 平台托管账号（邮箱 + 密码 / 短信验证码 / SSO 转发）
  // oauth   = 外部 IdP（企业微信 / LDAP / OIDC）
  "auth": {
    "mode": "builtin",
    "loginMethods": ["email", "sms"],
    "loginPath": "/login",
    "allowSignup": false,
    "roles": ["viewer", "editor", "admin"]
  },

  // ── 数据模型 ──
  "models": [
    {
      "name": "feedback",
      "fields": [
        { "name": "title",   "type": "string", "required": true },
        { "name": "body",    "type": "text" },
        { "name": "status",  "type": "enum",
          "options": ["new", "processing", "done"], "default": "new" },
        { "name": "rating",  "type": "number" },
        { "name": "ownerId","type": "string", "ref": "user" }
      ],
      // 谁可以读 / 写 / 改 / 删
      "permissions": {
        "read":   ["owner", "role:admin", "role:editor"],
        "create": ["role:viewer", "role:editor", "role:admin"],
        "update": ["owner", "role:editor", "role:admin"],
        "delete": ["role:admin"]
      }
    }
  ],

  // ── 平台能力申请（全部要管理员审批）──
  "capabilities": {
    "storage":   { "mode": "platform" },   // 数据存平台
    "files":     { "maxSizeMb": 10 },
    "outbound":  {                          // 允许访问的外部域名白名单
      "allow": ["api.example.com"],
      "mode": "deny"                        // 默认拒绝
    },
    "email":     { "templates": ["notify-owner"] },
    "realtime":  { "enabled": false }       // 第二步能力，默认关
  },

  // ── 页面 ──
  "routes": [
    { "path": "/",        "entry": "index.html" },
    { "path": "/login",   "entry": "login.html" },
    { "path": "/admin",   "entry": "admin.html", "requiresRole": "admin" }
  ]
}
```

### 2.1 设计要点

- **Manifest 是声明，不是代码**。平台按声明生成 API 与权限校验，用户代码只负责调 SDK。
  这是"平台掌控力"的核心来源，也是所有准入判定的唯一事实来源（对应 JarvisHub 的 capability manifest）。
- **能力申请默认拒绝**（`outbound.mode = "deny"`）。静态站点今天能任意 fetch 外部域名 ——
  换成应用形态后这是主要滥用面，必须显式申请。**所有能力调用都经过平台代理层**，
  不在 SDK 层做判定（SDK 可被用户改写）。
- **`ref` 字段做引用完整性**：模型间引用（如 `ownerId → user`）由平台写入时校验，避免脏数据。
- **manifest 版本化**（`version`）：加字段只升版本，老 manifest 继续按 v1 语义解释。
- **dev/prod 同一份 manifest**：环境只切数据，不切结构；避免"测试环境能跑、生产字段缺失"。

## 3. 平台托管 API

所有应用的数据访问走**同一组端点**，鉴权用应用级 token：

```
POST   /api/v1/apps/{app_id}/auth/login        → 换取 access token
POST   /api/v1/apps/{app_id}/auth/signup       → （allowSignup 时）
GET    /api/v1/apps/{app_id}/me                → 当前主体 + 角色

GET    /api/v1/apps/{app_id}/data/{model}      → 列表（带过滤/分页）
POST   /api/v1/apps/{app_id}/data/{model}      → 新建
GET    /api/v1/apps/{app_id}/data/{model}/{id}
PATCH  /api/v1/apps/{app_id}/data/{model}/{id}
DELETE /api/v1/apps/{app_id}/data/{model}/{id}

POST   /api/v1/apps/{app_id}/files             → 上传（返回受权 URL）
GET    /api/v1/apps/{app_id}/files/{file_id}

GET    /api/v1/apps/{app_id}/events            → SSE 实时订阅（第二步，capabilities.realtime）
```

### 3.1 鉴权模型

先按业界共识把**三种凭证**分清（Supabase / Lovable / Bolt 同款，本方案对齐）：

| 凭证 | 回答什么 | 能否进前端代码 | 权限边界 |
|------|----------|----------------|----------|
| **公开钥匙**（publishable，旧称 anon） | 哪个应用在调 | 可以，设计上就是公开的 | 低权限，只到达 RLS 允许的行 |
| **用户令牌**（终端用户 / 管理员） | 谁在调 | 登录后在 HttpOnly cookie 或内存，不落 localStorage | 证明身份，**不携带角色/租户归属** |
| **私密钥匙**（secret / service_role） | 服务端自己调 | **绝不能**，绕过 RLS | 全库权限，泄露即全库失守 |

> 行业动向：Supabase 2026 年底弃用 anon / service_role 旧密钥，改用 publishable / secret
> （短字符串、非 JWT）；新私密钥匙从浏览器发出会被按 User-Agent 拒绝（HTTP 401）。
> 本方案虽自建鉴权，但**沿用同一分档**：前端凭证默认低权限 + RLS 兜底，能绕过 RLS 的密钥永不进生成产物。

- **终端用户 token**：由 `POST /auth/login` 换取，payload 含
  `{ app_id, user_id, exp }`。默认 24h。**不在 token 里放角色/租户归属**
  —— 角色与 membership 从库里实时查（Supabase 明确警告：JWT 中的 claim 可能过期，
  被移除的成员仍能访问到 token 刷新为止）。
- **应用 token**：服务端调用（用户在自己的后端调平台 API 时用），
  由 `api_keys` 体系扩展而来，带 `app_id` 作用域与 Scoped 权限。这是上表的"私密钥匙"档，
  只留在用户自己的服务端；生成的静态站点接触不到它。
- **平台管理员**：任何 app 端点都接受管理员身份（审计与救场）。

**关键点**：权限判定只发生在平台端。用户代码里的 `if (user.isAdmin)` 只是 UI 表现，
不是安全边界 —— 数据接口会再判一次。

### 3.2 行级权限

`permissions` 字段里的 `owner` 语义：**记录归属者等于当前用户**。

```
can(user, "feedback", "update", record) =
    record.ownerId == user.id  OR  user.roles ∩ {editor, admin} ≠ ∅
```

角色从 `app_memberships` 实时查询，平台在查询层直接注入条件，不依赖用户代码过滤。

### 3.3 实时能力（第二步可选）

秒哒把实时协同作为核心三模块之一。AgenticOS 已有 SSE 基础设施，第二步可低成本提供：

- `GET /events?model=feedback` 订阅数据变更，按 3.2 的权限过滤后才推送；
- 只推事件不推全量数据（"记录 X 变更"），客户端按需回查；
- 默认关闭，必须 `capabilities.realtime.enabled = true` 且管理员批准。

## 4. 前端 SDK

给生成的网站代码用的浏览器 SDK（也可用于 Node 侧）：

```js
// 注入到页面的全局：window.AgenticOS
const { auth, data, files, events } = window.AgenticOS;

// 登录
await auth.login({ email: 'a@b.com', password: '…' });
const me = await auth.me();          // { id, email, roles: ['editor'] }

// 数据（CRUD 走平台，权限由平台判）
const list = await data.feedback.list({
  where: { status: 'new' },
  order: { createdAt: 'desc' },
  limit: 20,
});
await data.feedback.create({ title: '卡顿', body: '…', status: 'new' });
await data.feedback.update(id, { status: 'done' });

// 文件
const up = await files.upload(fileBlob);

// 实时（第二步，需 capability 批准）
const off = events.subscribe('feedback', () => data.feedback.list());
```

SDK 特点：

- **零配置**：页面里 `<script src="/sdk/agenticos.js">` 即可，不需要写 key
  （token 走 HttpOnly cookie 或内存）。呼应美团 NoCode 的"轻量、零门槛"体验。
- **薄**：不做本地缓存、不做离线队列 —— 那些是应用自己的事，
  SDK 只保证"请求经过平台鉴权"。
- **体积目标 < 20KB gzip**。

### 4.1 与 AI 提示词的衔接

沿用 2.0 的思路：提示词里注入的是**能力摘要 + 业务语义**，不是让用户填字段：

```
本应用可使用平台托管能力（通过 window.AgenticOS）：
- 数据模型：feedback（标题必填；状态：新/处理中/已完成；评论归作者所有）
- 权限：作者可改自己的反馈，编辑/管理员可改全部，仅管理员可删
- 认证由 SDK 负责。不要把任何 key 或 token 写进前端代码；
  所有数据请求必须走 window.AgenticOS，禁止直接 fetch 平台数据端点。
```

## 5. 权限与审批流

### 5.1 管理员审核什么

发布申请时，manifest 与普通网站**分开审**：

| 审核项 | 依据 | 风险级别 |
|--------|------|---------|
| 数据模型是否合理 | manifest.models | 低 |
| 权限声明是否过宽 | manifest.models[].permissions | **中** |
| 外部域名白名单 | manifest.capabilities.outbound.allow | **高** |
| 认证方式 | manifest.auth | 中 |
| 代码本身 | 既有源码扫描 + AI 评审 | 中 |

**过宽的权限要能一眼看出来**。例如 `read: ["*"]` + `create: ["*"]` +
`outbound.allow: ["*"]` 组合 = 开放代理，必须人工细看。

### 5.2 plan/apply 变更计划（本次新增，借鉴 SimpleBase）

审批对象从"manifest 快照"升级为"**变更计划**"。平台 diff 当前生效版本与申请版本，
生成只读计划：

```
App #7 变更计划（v1 → v2）
  ~ feedback.fields.rating : number（新增）
  + model comments          （新建）
  = feedback.permissions    （无变化）
  ! outbound.allow          [api.example.com → *]   ⚠ 风险升级
  - route /legacy           （删除）
```

- **批准 = apply**，apply 幂等：重复执行全部 skip，先查后写。
- 管理员可对 plan **逐项收紧**（见 5.4），收紧后的 plan 才是实际生效版本。
- 每次 apply 落一条不可篡改的审计记录（谁批的、批了哪一版、diff 是什么）。

这比原方案"审快照"更强：**权限悄悄扩大会在 diff 里显形**，且支持安全的重复提交。

### 5.3 状态机

```
draft ──申请发布──▶ pending ──批准(apply)──▶ deploying ──▶ deployed
                       │                              │
                       └──拒绝──▶ rejected            │取消
                                                       ▼
                                                    cancelled
                                                       │
                                          重新提交（新版本）
                                                       ▼
                                                  superseded
```

与现有 `website_deploys` 状态机一致（已有 `pending/approved/deployed/
rejected/cancelled/superseded/failed`），可直接复用审批队列 UI，只增加 plan 展示区。

### 5.4 权限收敛

批准时允许管理员**收紧** plan（例如去掉 `outbound.allow` 的某几个域名、
把 `create: ["*"]` 改为 `create: ["role:viewer"]`）。收紧后的版本才是实际生效版本 ——
"申请什么"与"批什么"分离，避免用户改一版就多要一点权限。

## 6. 数据存储

### 6.1 隔离模型决策（本次重写）

原文建议"每应用一张物理表"。调研后修正为**分档策略**：

| 方案 | 优点 | 代价 | 适用 |
|------|------|------|------|
| A. 每应用物理表（原方案） | 真实列与约束、易导出 | 表数量爆炸（apps × models）；迁移 fan-out；DDL 动态生成风险 | 不推荐作为默认 |
| B. schema-per-app | 强逻辑隔离、每 app 可自定义表结构；导出/删除按 schema 简单 | schema 多时迁移 fan-out；Postgres ~1000 schema 后开始吃力；连接池复杂 | 大客户 / 强自定义 |
| **C. 共享表 + `app_id` + RLS（推荐默认）** | 一张表服务所有 app；迁移一次生效；成本最低；DB 内核强制隔离 | 列约束弱（靠 API 层校验）；大表有 noisy-neighbor | **默认档，覆盖绝大多数生成应用** |
| D. 独立数据库 | 物理隔离、合规最强 | 运维成本线性增长；早期创业陷阱（业界共识） | 企业级付费/合规客户 |

**推荐主档 C 的落地形态**：

```
app_records (
  app_id      uuid not null,        -- 应用隔离（RLS 第一层）
  env         text not null,        -- dev | prod（环境隔离）
  model       text not null,        -- feedback / comments ...
  record_id   uuid not null,
  owner_id    uuid,                 -- 行级归属（RLS 第二层）
  data        jsonb not null,       -- 业务字段，按 manifest 在 API 层校验
  created_at  timestamptz,
  updated_at  timestamptz,
  primary key (app_id, env, model, record_id)
);
create index on app_records using gin (app_id, env, model, data jsonb_path_ops);
alter table app_records enable row level security;
```

- **字段校验放在 API 层**：所有写入都经过平台 API，按 manifest 用 JSON Schema 校验
  类型/必填/枚举/引用完整性。DB 层用 JSONB 提供灵活性与 GIN 索引提供过滤能力。
  "约束弱"由"平台掌控唯一写入口"弥补 —— 用户代码无法直连数据库。
- **RLS 兜底**：万一 API 层有 bug，数据库仍按 `app_id` + `owner_id` 拒绝越权行（见 6.3）。
- **升级路径**：当某 app 需要强隔离/真实列约束时，可平滑迁移到 B 或 D 档，API 不变。
  这是 Supabase 的通用做法（共享表为主，独立库留给有合同要求的客户）。

### 6.2 环境隔离

- 默认档用 `env` 列（`dev` / `prod`）区分，查询强制带 env；
- 隔离档用 schema 后缀（`app_7_dev` / `app_7_prod`）或独立库；
- **dev 数据永不进入 prod**；管理员可一键清空 dev，prod 删除需二次确认；
- 审批与 plan/apply 默认作用于 prod，dev 可自助 apply（仍需过 manifest schema 校验）。

### 6.3 行级安全的双保险（按 Supabase 正确姿势修正）

原文用 `current_setting('appic.user_id')` 加 `roles LIKE ANY` 内联判断，
在共享表场景下应改为：

```sql
-- ① membership 表（角色与归属实时查，不放 JWT）
create table app_memberships (
  app_id  uuid not null,
  user_id uuid not null,
  roles   text[] not null default '{}',
  primary key (app_id, user_id)
);

-- ② helper 函数放非暴露 schema + 空 search_path，避免递归 policy 与注入
create schema if not exists appic_private;
create or replace function appic_private.my_roles(p_app uuid)
returns text[] language sql stable security definer set search_path = '' as $$
  select coalesce(array_agg(role), '{}')
  from unnest((select roles from app_memberships
               where app_id = p_app and user_id = auth.uid())) as role;
$$;

-- ③ RLS policy：app_id 由会话设定，owner 或角色放行
create policy record_read on app_records for select to authenticated
using (
  app_id = current_setting('appic.app_id', true)::uuid
  and env = current_setting('appic.env', true)
  and (
    owner_id = auth.uid()
    or appic_private.my_roles(app_id) && array['editor','admin']
  )
);
```

要点（来自 Supabase 多租户指南）：

- 租户归属从 **membership 表**查，不从 JWT claim 读（JWT 过期窗口会越权）；
- 视图需 `security_invoker = true`，否则以拥有者权限绕过 RLS；
- helper 函数 `security definer` + 空 `search_path`，放非暴露 schema；
- 读写各一条 policy（`using` 控读、`with check` 控写），写也要隔离；
- 测试策略像测试代码一样做（双租户 pgTAP 用例）。

RLS 不是必须的（API 层判已正确），但在"应用层出 bug"时能兜底，成本很低。

### 6.4 存储引擎

**第一步建议 PostgreSQL**：JSONB + GIN 索引、RLS 原生、`uuid` 类型，
与上述设计完全契合。若必须沿用 MySQL，则退化为 `JSON` 列 + 应用层过滤 +
API 层强制校验，权限判定复杂度不变但失去 DB 层兜底。

## 8. 实施路线（建议分三步）

### 步骤 1：数据与鉴权底座（不动发布链路）

1. `apps` / `app_users` / `app_memberships` 三张表；
2. `POST /auth/login` 签发应用级 token（复用 `create_access_token`，加 `app_id` scope，
   **不含角色 claim**）；
3. `app_records` 共享表 + GIN 索引 + RLS policy；
4. CRUD 端点 + API 层 manifest Schema 校验 + 行级权限判定；
5. dev/prod 的 `env` 隔离落地。

**完成后静态网站就能"登录 + 存数据"** —— SDK 是纯前端 JS，静态站点不用改部署方式。

### 步骤 2：Manifest 生成 + plan/apply 审批

1. manifest JSON Schema 与解析器；
2. **AI 生成链路**：需求文档 → manifest 草稿 → 对话确认（2.0）；
3. 发布流程识别 `agenticos.app.json`，走独立审核队列；
4. plan diff 生成与展示（5.2），审批 UI 增加"权限审阅"分区；
5. 批准时 apply 收紧后的 plan，落审计。

### 步骤 3：运行时 / 实时（按需，可能永远不做）

只有出现真实需求时才做：

- SSE 实时订阅（3.3，成本最低，优先）；
- 用户函数托管（受限运行时，无网络或受限网络、CPU/时长限额）；
- 定时任务（cron）；
- webhook 入站。

## 9. 安全清单（实现时逐条对照）

- [ ] 所有 app 端点校验 token 的 `app_id` 与路径一致（防跨应用越权）
- [ ] 所有 app 端点校验 token 未过期、未吊销
- [ ] **角色/归属从 membership 实时查，不信任 JWT claim**
- [ ] **每张含用户数据的表都真正开启 RLS**（调研中 Lovable/Bolt 脚手架最常踩的坑就是
  RLS 没开或写成 `using(true)`，等于没设防、改个 URL 参数就能看别人的数据）
- [ ] **令牌存 HttpOnly cookie 或内存，不进 localStorage**（XSS 一发即可盗号）；
  刷新后仍能登录（接好 `onAuthStateChange` / 自动刷新），避免"预览能用、部署就掉线"
- [ ] 行级权限在**查询层 + RLS** 双重注入，不依赖用户代码
- [ ] RLS policy 读写分离（`using` / `with check`），视图用 `security_invoker`
- [ ] helper 函数 `security definer` + 空 `search_path`，放非暴露 schema
- [ ] 出站域名白名单在**平台代理层**强制（不是 SDK 层）
- [ ] 所有能力调用统一过平台门卫，SDK 改写无法绕过
- [ ] manifest 必过 JSON Schema 校验才进审批
- [ ] plan/apply 幂等；审批只能收紧不能放宽；每次 apply 落不可篡改审计
- [ ] 上传文件做类型与大小校验，存储路径不可遍历
- [ ] 审计日志记录：谁（主体）、对什么（模型）、做了什么（CRUD/plan apply）、结果
- [ ] 令牌不写日志；API Key 哈希存储（Scoped Key）
- [ ] 管理员可导出/删除应用数据（合规要求）；dev 可自助清空、prod 需二次确认
- [ ] 应用删除时物理清理数据、文件与 membership（不留孤儿）

## 11. 已定结论与遗留问题

**已定结论**（本次调研后确认）：

1. **终端用户身份**：独立 `app_users` + `app_memberships`，不复用平台账号体系
   （外部客户不应被迫注册 AgenticOS 账号）；租户归属实时查库，不读 JWT。
2. **隔离档位**：共享表 + RLS 为默认；schema-per-app / 独立库为大客户升级路径。
3. **实时**：列为第二步，默认关闭，需 capability 批准。

**遗留问题**：

1. **配额与计费**：外部终端用户的写操作是否计入平台成本？秒哒采用"后端资源分级"，
   美团 NoCode 明确不商业化。建议先按 app 维度限流，计费后置。
2. **跨应用共享数据**：暂不做。若出现"看板要从另一个应用取数"，
   设计"应用间授权"而非让用户直连数据库（对应 JarvisHub 的 execution grant）。
3. **隐私合规**：终端用户数据归属、删除应用时是否通知外部用户，需法务确认。
4. **开源组件许可证**：若引入 Dify/FastGPT/n8n 类组件，先核对附加条款
   （多租户授权、品牌保留、商用限制）。

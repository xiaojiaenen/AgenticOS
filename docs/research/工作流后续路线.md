# 工作流引擎后续路线

> 状态：v2 已上线（条件分支 / 并行 fan-out / 人工输入屏障 / 快照恢复 / 拖拽画布）。
> 本文记录**尚未实现**的两项能力，以及实施时需要注意的约束。它们是产品
> 决策级别的改动，不建议顺手加进现有引擎。

---

## 1. 循环节点（子流程迭代）

### 为什么不做成「回边」

最直观的想法是允许环（比如 condition 的 false 分支指回上游），引擎按
「节点被多次执行」处理。**明确否决**，原因：

- **终止条件无处表达**。回边方案里「循环几次」只能靠节点内部状态或一个
  全局计数器节点隐式表达，工作流定义里看不出终止条件 —— 管理员无法在
  图上回答「这个循环什么时候停」。
- **恢复语义失效**。v2 的暂停/恢复快照是「每个节点一个终态 + 一份输出」。
  回边让同一节点有多次执行、多份输出，快照必须变成「执行序号 → 输出」，
  与 `waiting_node_id` 的单值暂停点模型冲突。
- **校验与死循环**。环检测目前是硬性拒绝（`validate_workflow_graph`
  的 Kahn），放行后需要另设迭代上限，否则一个写错的图能烧光预算。

### 建议形态：显式的 loop 节点 + 子图

对齐 Dify 的 Iteration / Loop 节点 —— **循环是容器，不是边**：

```
[loop]  params:
          items:   "{{nodes.retrieve.output.results}}"   # 或被引用的子图 id
          max_iterations: 20                              # 必填，硬上限
          concurrency: 1                                  # 1 = 串行
          subflow: { nodes: [...], edges: [...] }         # 子图，自带 start/end
```

- **每轮独立上下文**：子图里的 `{{item}}` 指向当轮元素，`{{index}}` 指向序号；
  子图内部变量不能泄漏到外层，外层变量可只读访问。
- **输出是数组**：loop 节点输出 `[每轮 end 节点的 output]`，下游用
  `{{nodes.loop.output}}` 引用整体，或 `{{nodes.loop.output.0}}` 取单轮。
- **校验**：loop 的 `subflow` 本身要过一遍 `validate_workflow_graph`
  （递归校验，注意给子图单独的节点 id 命名空间，避免与外层冲突）。
- **执行**：`max_iterations` 必填且设硬上限（建议 ≤ 100）；`concurrency > 1`
  时按批 `asyncio.gather`，与 v2 已有的批量并发复用同一套错误收集逻辑。
- **恢复**：loop 节点是**原子**的 —— 执行中就绪的人工输入仍然走屏障，
  但 loop 本身不能在迭代中途暂停（快照粒度保持「节点级」）。若确需中途
  人工输入，把 human_input 放进子图里，并在恢复时重跑整个 loop（幂等要求
  写进文档）。
- **预算**：loop 必须参与 run 级预算（`AGENT_BUDGET_*`）与总超时，
  否则 20 轮 LLM 调用极易撞穿预算。

### 工作量估计

引擎（渲染 + 校验 + 执行 + 快照）× 约 400 行；画布（loop 节点的子图编辑，
可先只支持 JSON 编辑）× 约 200 行；测试约 20 个用例（终止、并发、错误传播、
恢复重跑、预算）。**建议单独立项**，不要在改引擎稳定性时混进来。

## 2. ARQ 多 worker 部署形态

### 现状

工作流的**后台执行**（`service.launch_run` / `launch_resume`）用的是进程内
`asyncio.create_task`，在 `_BG_TASKS` 里持强引用防 GC。单进程部署下完全够用：

- 后端重启 → `startup_cleanup` 把 `running` 行收尸为 `failed("restart")`；
- `waiting_input` 的暂停点持久化在 DB（`context_json` + `steps_json`），
  重启后照常可恢复。

### 多 worker 下的问题

Uvicorn `--workers N` 或 K8s 多副本时，进程内任务有三个缺口：

1. **执行归属不可见**：run 行只记 `status`，不记「哪个 worker 在跑」。
   运维看到 `running` 无法判断它在哪个副本、是否还活着。
2. **无法取消**：管理端没有任何手段终止一个卡住的 run（没有跨进程取消通道）。
3. **收尸误伤**：一个 worker 重启会把**所有** `running` 行标成
   `failed("restart")` —— 包括其他 worker 正在正常执行的 run。

### 建议方案：把执行搬进 ARQ

项目已有 ARQ worker（`app/services/task_queue.py`，跑 PPTX 导出、文档编译、
网站构建等）。工作流执行迁过去即可复用现有的任务调度与重试：

- **任务定义**：`execute_workflow_run(run_id)` —— 现在就有的
  `service.execute_run_background` 签名几乎不用改，直接注册进 ARQ。
- **入队**：`launch_run` 里把 `_schedule_background(...)` 换成
  `arq_pool.enqueue_job("execute_workflow_run", run_id)`。
- **归属标记**：`workflow_runs` 加 `worker_id` / `heartbeat_at` 两列；
  执行期间每 30s 更新心跳。收尸逻辑改为「心跳超时的 run 才标记 failed」，
  不再一刀切标记所有 `running`。
- **超时**：ARQ 的 `job_timeout` 要大于 `WORKFLOW_RUN_TIMEOUT_SECONDS`，
  让引擎自身的优雅超时（落 failed + 步骤轨迹）先到。
- **取消**：`arq` 的 `abort_job` 打通一个 `POST /workflows/runs/{id}/cancel`
  端点；本地 `asyncio.create_task` 形态保留为「ARQ 不可用」的降级路径。
- **工具桥不受影响**：智能体调用工作流仍是**内联执行**（模型要等最终结果），
  与后台执行通道无关。

### 迁移风险

- ARQ 不可用时必须降级回进程内执行（现有 `_schedule_background` 逻辑保留），
  否则「Redis 挂了 → 所有工作流不能跑」。
- 心跳与收尸要一起改，只改一半会出现「run 永远 running」。
- 需要一次数据迁移给存量 `running` 行补 `worker_id = NULL`（视为已失联）。

### 工作量估计

任务注册 + 入队改造 + 心跳/收尸 + 取消端点 ≈ 250 行；迁移 1 个；
测试约 10 个用例（入队/降级/心跳超时/取消/与工具桥隔离）。
**建议与部署拓扑决策一起做** —— 单实例部署下没有收益。

## 附：当前引擎的已知边界（非缺陷，是设计选择）

| 边界 | 说明 |
|---|---|
| 无环 | 循环用 loop 节点表达（见上），不开放回边 |
| 人工输入是屏障 | 其它节点全部终态后才提问；不支持「一边跑一边问」 |
| 快照是节点级 | 中途暂停的恢复重跑整个 loop（引入 loop 后） |
| http 节点禁重定向 | 重定向目标不再过 SSRF 校验，跟随等于绕过 |
| 知识节点按触发者 ACL | 工作流不能提权检索 |

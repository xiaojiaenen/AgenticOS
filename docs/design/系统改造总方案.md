## 0. 一页纸看懂（执行摘要）

### 0.1 现状判断

AgenticOS 是一个**功能相当完整、工程质量不低**的 AI Agent 平台：约 30 个 API 端点模块、60+ 服务、20+ 工具、134 个测试文件、后端约 9.6 万行 / 297 个 py 文件。对 wuwei 的已知缺陷有补丁层 + 回归测试兜底，Alembic 迁移幂等性有纪律。**这不是一个需要推倒重来的项目。**

但积累了三类问题：

1. **框架底座绑死在 wuwei 3.4.1**：核心 6 文件 4200+ 行、补丁层 688 行兜 17+ 个上游 bug、94 处引用。这是最大的耦合点和长期维护负担。
2. **大量"通用能力自研"**：JWT、密码哈希、内存 Redis、限流、BM25 检索、重排、RAG 全链路、审批状态机——这些业界已有成熟库/框架，自研版在功能与可维护性上都不划算。
3. **横切工程债**：async 路径混同步阻塞、前端 27 个手写 service、任务队列废弃 shim 待清理（已迁 TaskIQ）、Redis 内存 fallback 在多实例下静默退化、启动迁移失败不阻断。

### 0.2 改造总目标

> **把"自研一切"改造成"成熟生态 + 薄业务层"**：通用能力交给久经考验的开源库/框架，自研只保留真正的差异化资产（业务鉴权、记账口径、SSE 契约、企业 Cookie 网关、用户交互）。

### 0.3 五条改造战线

| 战线 | 一句话 | 优先级 | 改动量 | 详见 |
|---|---|---|---|---|
| **A. 框架底座** | wuwei → LangGraph（编排）+ DeepAgents（harness） | P0 | 极大（重写核心） | 第 4 章 |
| **B. 自研归位** | JWT/哈希/Redis/重排/网关等换成成熟库 | P0 | 小-中 | 第 5 章 |
| **C. 数据演进** | SQLite/MySQL → PostgreSQL（+pgvector） | P1 | 中 | 第 6 章 |
| **D. 能力增强** | 接入纯库/本地工具（OTel SDK / SOPS / FlashRank / LiteLLM SDK） | P1 | 小-中 | 第 7 章 |
| **E. 后台管理** | 管理端功能与体验优化 | P1 | 中 | 第 8 章 |

横切工程改进（async 阻塞、前端契约、CI/可观测/安全）贯穿所有战线，见第 9 章。

### 0.4 关键决策矩阵（用户需拍板）

| 决策 | 建议 | 影响 |
|---|---|---|
| 是否全量替换 wuwei | 是，但用**绞杀者模式渐进 + 双轨回退**，不全量 all-in | 战线 A 的启动方式 |
| 底座选谁 | **LangGraph 主底座 + DeepAgents 做 harness**；HITL 优先用 DeepAgents `interrupt_on`，Beta 期用 LangGraph `HumanInTheLoopMiddleware` 退路 | 战线 A 的框架选型 |
| RAG 是否自研 | **不自研**，检索/索引交给 LlamaIndex，编排 LangGraph，评估 RAGAS，重排 FlashRank/bge | 战线 A/B 的 RAG 方案 |
| 数据库 | PG 定为**生产推荐 + 未来默认**，开发继续 SQLite，收益拐点再迁存量 | 战线 C 的节奏 |
| 能否接受大改动 | **能**（用户明确），因此不因"改动大"而保留自研 | 全局原则 |

### 0.5 一句话路线图

**先做低风险高收益的"自研归位"（JWT/哈希/前端契约/重排），同步搭好新引擎适配层与行为基线；审批和 RAG 直接用现成框架替换自研；数据层补 PG 双轨、择机迁移；后台管理按 P0/P1 补齐；全程双轨可回退，每阶段独立验收。**

## 1. 现状全景

### 1.1 技术栈

| 层 | 现状 |
|---|---|
| 后端 | Python 3.13 + FastAPI + SQLAlchemy 2.0 + Alembic + Pydantic Settings |
| 数据库 | 默认 SQLite（`config.py:77`），可选 MySQL(pymysql)；Redis 单机/集群/内存 fallback |
| AI 框架 | wuwei 3.4.1 + openai 3.40（HTTPX2）；企业 Cookie 网关 + Playwright 自动登录 |
| 前端 | React 19 + Vite 6 + TS + react-router + react-query + Zustand + Univer 1.4 |
| 任务队列 | arq + TaskIQ 双实现并存；MCP SDK；办公 Node 运行时（Univer） |

### 1.2 能力地图（9 大域）

认证与权限、Agent 核心编排、LLM 提供商与网关、工具系统、知识库与记忆、办公与产物（PPT/文档/表格/A2UI/chart/website）、工作流与多智能体、数据与基础设施、前端。逐模块现状与优化点见 `项目逐功能优化方案.md` 第 3 节。

### 1.3 核心矛盾

- **维护成本**：9.6 万行 + 200+ 自定义能力，且大量是与生态重复的自研通用件。
- **分布式一致性**：多处"进程内存态 + 注释'可接受'"（contextvar / `_turn_counts` / `_sessions` / Casbin 缓存），多实例部署隐患集中；Redis 内存 fallback 掩盖生产分布式依赖。
- **框架耦合**：wuwei 补丁层、adapter 适配层、MCP 自签客户端——换框架要重建这些语义。
- **AI 特有风险**：Prompt/工具/MCP/文件操作攻击面；沙箱是正则黑名单可绕过（P0 安全）；检索质量与 Token 成本缺看板。

## 2. 改造原则（贯穿所有战线）

1. **能用现成就用，哪怕改动大**——这是本次改造的第一原则，覆盖此前"风险最小化"的保守判断。仅当现成方案无法满足业务鉴权/计费/契约要求时，才保留自研，且自研层要尽量薄。
2. **绞杀者模式（Strangler Fig）**——新方案先在隔离入口接管小部分流量，验证后逐步扩大；旧通道始终保留可秒级回退，直到观察期结束。
3. **每阶段独立验收 + 独立回退**——禁止跨阶段合并提交导致无法定位回归。
4. **行为基线对拍**——改造前录制代表性会话/请求的输出作为 oracle，改造后逐项对拍。
5. **差异化资产不可丢**——业务鉴权（Casbin/visibility）、按 user 的用量记账、15+ SSE 事件契约、企业 Cookie 账号池、审批 UI/通知，无论换什么框架都必须原样保留。
6. **安全边界在工具层，不信任模型**——DeepAgents 明示 "trust the LLM"；换成现成框架不等于放松自研安全逻辑（沙箱、审批策略、SSRF 白名单必须保留并强化）。

## 3. 改造依赖关系（先做什么）

```
行为基线 + CI 矩阵（前置，所有战线都依赖）
        │
        ├──► 战线 B（自研归位）──┐  ← 低风险、可立即并行启动
        │      JWT/哈希/Redis/重排/前端契约
        │                        │
        └──► 战线 A（框架底座）──┤  ← 大工程，分 6 阶段
              适配层→SSE→HITL→RAG→多智能体→全量切换
                                 │
                    能力增强 D ───┤  ← OTel SDK/SOPS/FlashRank/LiteLLM SDK（均纯库，无外部系统）
                    数据演进 C ───┤  ← PG 双轨测试前置，向量库择机
                    后台管理 E ───┘  ← 依赖前面暴露的管理能力
```

**关键路径**：战线 A（框架底座）周期最长，应最早启动准备阶段（基线 + 依赖验证）；战线 B 可并行快速见效；战线 C 的"PG 双轨测试"要提前做，否则会卡住 A 的 RAG/向量方案。

## 4. 战线 A：框架底座现代化（wuwei → LangGraph + DeepAgents）

> 完整分析、能力映射表、6 阶段计划、13 项风险、来源附录见 `docs/design/wuwei迁移LangChain方案.md`。本章为决策摘要 + 立场修正后的要点。

### 4.1 结论

**这是一次"重写核心引擎"，不是"换个 import"。** 全仓 94 处引用 / 95 文件，核心 6 文件 4200+ 行；补丁层 688 行兜 17+ 个真实线上 bug，有 27 条回归测试；前端消费 15+ 种 SSE 事件是硬契约。

### 4.2 为什么现在要动（立场修正）

用户明确要求"能用现成就用，哪怕改动大"。原方案从"迁移风险最小化"出发建议渐进/保守；现按"长期维护成本最小化 + 拥抱生态"重新评估：

- DeepAgents 把 HITL / skills / memory / filesystem / subagents / MCP 全部内置——项目里好几套自研中间件可以直接换成框架能力。
- LangGraph + LlamaIndex + LiteLLM（仅 SDK）+ RAGAS 是 2026 年成熟生态，自研对应能力长期不划算；**但只引纯库形态，不引需单独部署的 Proxy/服务（见优化方案 3F.0）**。
- 代价是改动大、要引入多套框架、有版本管理成本——用户已明确接受。

### 4.3 框架分工（修正后）

| 职责 | 选型 | 成熟度 |
|---|---|---|
| 运行时/编排底座 | **LangGraph** 1.2.22 | Stable |
| Agent harness | **LangChain** `create_agent` 1.5.0 | Stable |
| 重型 harness（skills/memory/HITL/filesystem） | **DeepAgents** 0.7.39 | Beta（需 pin 版本；退路 LangGraph 原生） |
| 检索/索引 | **LlamaIndex** | 成熟（检索精度最优） |
| LLM 网关 | **LiteLLM Python SDK**（库形态，仅统一调用接口；**不用 Proxy**） | MIT 核心成熟 |
| RAG 评估 | **RAGAS** | 事实标准 |

> **harness 选型补充**（2026-11-17 联网调研，详见 `项目逐功能优化方案.md` 3D 节）：市面主流 harness 中，DeepAgents 是少数「模型无关 + 可嵌入 + MIT」的选项，选型无需推翻。Claude Agent SDK 是生产验证最充分的 harness（内置文件系统/shell/权限模式/hooks/skills/MCP/session 恢复），但**强绑 Claude 模型**，与本项目多提供商网关冲突，**不接入、只抄机制**——尤其 `permission mode` 语义（对齐三档审批）和 `hooks` 作为确定性策略点（拦截危险命令/审计/预算熔断，补 "trust the LLM" 安全短板）。Cursor/Cline/Aider 等是成品编程助手，不是可嵌入组件。

### 4.4 HITL 审批：用 DeepAgents 内置，删掉自研状态机

核实到的官方事实（详见迁移方案 9.2）：

- `interrupt_on={tool: config}` 声明式配置即启用；框架自动注入 `HumanInTheLoopMiddleware`。
- 四种决策 `approve / edit / reject / respond`，可配 `allowed_decisions` 和 `when` 条件中断（正好对应项目三档审批策略）。
- 中断时 `PatchToolCallsMiddleware` 自动修复 message history（覆盖部分补丁层 bug 语义）。
- 恢复：`Command(resume={"decisions": [...]})` + 同一 `thread_id`；**必须有 checkpointer 持久化**。
- 官方**不要求自建审批状态机**——应用只需展示动作、收集决策、按顺序回灌。

**改造动作**：把现有 `ApprovalManager` 的 Redis/DB 状态改造成 LangGraph checkpointer（Redis/Postgres），审批 UI / 通知 / 审计事件适配到新回调。原自研审批状态机大部分可删。

**退路**：DeepAgents 仍 Beta；若阶段执行时未稳定，用 LangGraph `HumanInTheLoopMiddleware`（Stable，能力同源）。

### 4.5 RAG：不应自研，用 LlamaIndex + LangGraph + RAGAS

业界共识（多来源一致）：**"LlamaIndex 管数据/检索 + LangGraph 管编排 + RAGAS 管评估"是 2026 生产 RAG 的主流混合栈**。

| 层 | 现成方案 | 自研部分（仅保留） |
|---|---|---|
| 检索/索引 | LlamaIndex（内置 hybrid search、automerging、rerank、160+ loader） | visibility / Casbin 行级鉴权（包在 retriever 外）、scope 过滤、与知识库模型的绑定 |
| 重排 | FlashRank（CPU 轻量）/ bge-reranker-v2-m3（多语言） | 无 |
| 编排 | LangGraph | agentic RAG 的状态机 |
| 评估 | RAGAS（纯库） | 不接 Langfuse（外部系统），用 OTel SDK 埋点写自己 DB |

**改造动作**：`knowledge/` 下 retrieval(888) / ingest_pipeline(526) / wiki_compiler(814) / rerank 中，检索与索引职责交给 LlamaIndex；自研只留业务鉴权外壳。**存量切片/embedding 格式对齐是"改动大"的主要来源。**

### 4.6 分阶段计划（摘要）

| 阶段 | 内容 | 验收 |
|---|---|---|
| 0 准备基线 | pin 版本、依赖冲突验证、录制 20-30 条会话基线 | 全量测试绿、基线入库 |
| 1 地基适配层 | LLM 网关（标准 provider→LiteLLM **SDK 库**）、消息/工具注册适配，先跑直通通道 | 直通对拍一致、工具元数据 100% 对齐 |
| 2 SSE + 单 Agent 循环 | SSE mapper（咽喉）、并发/截断/usage 等补丁语义移植 | 基线会话逐事件等价、补丁回归绿 |
| 3 HITL 审批 | DeepAgents `interrupt_on` + checkpointer（或 LangGraph 退路） | 审批全链路 + 并发/过期专项绿 |
| 4 RAG / 记忆 / 多智能体 / MCP | LlamaIndex 接管检索、DeepAgents skills/memory、LangGraph 多智能体 | 检索质量不降、会话恢复/MCP 对拍通过 |
| 5 全量切换 + 退役 | 100% 切流、观察期 2-4 周、删 wuwei 依赖 | 无生产代码命中 wuwei、P0/P1 故障为零 |

### 4.7 工作量与风险

- 原估 9–16 人周（按大量自研）；改用现成框架后**总工时可能下降，但引入 5 套框架的集成/回归成本会补回来，净变化需重新评估（需验证）**。
- 最高风险：SSE 事件契约、审批改参/跨 worker 正确性、补丁 bug 语义重建、openai 3.x 与 langchain-openai 依赖冲突（**落地前必须验证**）、LlamaIndex 与现有鉴权/数据模型整合。

### 4.8 多智能体架构要不要改（2026-11-17 排查）

**结论：不需要大改，按"活的保留、死的清理、边界对齐"处理。** 先厘清项目里其实有 4 套"多智能体相关"实现，状态差别很大：

| 实现 | 规模 | 真实状态（代码核实） | 处置 |
|---|---|---|---|
| **workflow 引擎**（`workflow/`） | engine 581 + nodes 223 + service 535 | **活的生产代码**：被 `/workflows` endpoint 和 agent factory 真实调用；纯计算调度器（无关 LLM/DB/HTTP 依赖），8 类节点、fan-out 并行、屏障式 human_input、DB 唯一事实源、受限变量解析防注入；借鉴 Dify/Coze 节点流 | **保留自研**——设计精良、与 LangGraph 职责不同（这是用户可配置的业务工作流，不是 Agent 编排）；迁移 LangGraph 无收益、风险高 |
| **异步子智能体**（factory `AsyncSubAgent`） | 内嵌 | 活的，用 wuwei `AsyncSubAgent`/Middleware | **随框架迁移换 DeepAgents `task`**（同步/异步并行子智能体），同构替换 |
| **multi_agent_ppt_service** | 317 行 | **实验/死代码**：docstring 说"Swarm+TeamMember"，实际只用 `LLMGateway`+`ToolRegistry` 手写三 Agent 串行循环；**无任何生产调用方**，只有 `test_new_modules.py` 在测 | **删除或搁置**，不必为它做迁移 |
| **ppt_pipeline**（wuwei StateGraph） | 228 行 | **半成品死代码**：`_create_artifact_node` 未接真实服务，无生产调用方，只有测试 | **删除或搁置** |

**为什么 workflow 引擎不该换 LangGraph**：两者看着像（都是图编排），但职责不同——本项目 workflow 是**管理员在后台配置的确定性业务流程**（节点 JSON 定义、变量受限路径、暂停恢复落库），LangGraph 是**开发者写代码定义的 Agent 编排**。2026 业界共识也是"任务确定性越高越该用工作流，不确定性越高才需要代码框架"（见来源）。把精良的自研确定性引擎换成代码式 LangGraph 属于降级；正确做法是让两者并存：确定性流程走 workflow 引擎，Agent 自主编排走 DeepAgents/LangGraph。

**真正要改的只有一处**：`PPT 主路径目前是 Agent + ppt_tools 逐页生成 SVG`（单 Agent），若未来要上"多 Agent 协作生成 PPT"，直接用 DeepAgents `task`/LangGraph supervisor 重写那个死代码即可，**不要复活旧的 wuwei Swarm 写法**。

> 联网依据：LangGraph 原生 supervisor/subgraph/Send API 适合复杂多智能体；Dify/Coze 是低代码工作流平台；"确定性任务用工作流、不确定性任务用代码框架"是 2026 主流决策框架。来源见优化方案 3F 节。

## 5. 战线 B：自研组件归位（能换现成就换）

> 完整映射表、许可证核实、落地优先级见 `项目逐功能优化方案.md` 第 3B 节。

### 5.1 直接换（低风险，立即做）

| 自研 | 换成 | 许可证 | 备注 |
|---|---|---|---|
| 手写 JWT | PyJWT | BSD | 不用 python-jose（CVE 前科） |
| PBKDF2 哈希 | argon2-cffi | MIT | passlib 已停维护；存量双验过渡 |
| MemoryRedis | fakeredis | BSD-3 | 仅开发/测试 fallback |
| 启发式重排 | FlashRank / bge-reranker / rerankers | Apache-2.0 | 避开 jina CC-BY-NC 商用坑 |
| 任务队列废弃 shim | 清理 `task_queue.py` 空壳 | — | 已迁 TaskIQ、arq 依赖已删，只剩兼容门面待清 |

### 5.2 部分换 / 谨慎

- **LLM 网关**：标准 provider 统一调用走 **LiteLLM Python SDK（库，零部署）**；**不用 Proxy**（其虚拟 key/预算/成本看板是外部服务能力，本项目已自研用量记账/网关/并发闸，不需要）。只保留企业 Cookie 账号池这一小块自研。
- **沙箱**：必须换真隔离——这是安全底线。nsjail（轻）→ gVisor（中）→ Firecracker/Kata（强），按代码可信度分级；公网多租户直接上微虚拟机。**做成可选后端并保留内存 fallback**，避免与 macOS 本地开发冲突。

### 5.3 保留自研（真的换不掉）

审批 UI/通知（框架只给状态机）、按 user 的用量记账口径、15+ SSE 事件契约、业务鉴权（Casbin/visibility）、差异化的 MCP 凭据注入与 SSRF 白名单。

> 注：审批**状态机**已改为用 DeepAgents（4.4），这里保留的是审批的**业务外壳**。

### 5.4 框架内置能力替代自研（深度排查，2026-11-17）

用户诉求：「DeepAgents / LangGraph 有的就不要自研，哪怕改动大」。本节逐项核对代码 + 官方文档后给出结论。
**核心认知纠正**：项目并非「什么都自研」——很多能力的**加载/执行层本来就是框架（wuwei）提供的**，真正自研的只是**管理层 + 业务外壳 + 提示词胶水**。迁移时要删的是后者，不是把整个能力重写。

#### 5.4.1 技能系统（用户重点问：为什么要自研？）

**答：技能「加载」从来没自研，用的是 wuwei 插件；自研的只有「管理」和一句提示词。** 三层拆解：

| 层 | 现状 | DeepAgents 对应 | 处置 |
|---|---|---|---|
| ① 加载/按需读取 | `factory.py` 用 `setup_skill_plugin` + wuwei 的 `SkillManager`/`FileSystemSkillProvider`，暴露 `list_skills`/`load_skill` 两个工具 | 内置 `SkillsMiddleware`，同样「启动时只读 name/description，命中才读全文」，机制几乎一模一样 | **删 wuwei 插件，换框架 Skills**（改动小、行为等价） |
| ② 管理（CRUD/zip 上传/DB/后台 UI/画像绑定） | `skill_service.py` 394 行 + `data/skills/` 22 个技能 + `skills` 表 + 后台面板 | 框架**没有**——DeepAgents 只读目录里的 SKILL.md，不管 DB/上传/权限/按画像装配 | **保留自研**，但改成「管理磁盘上的 SKILL.md 目录」，DB 退化为索引/元数据 |
| ③ 提示词注入 | `SKILL_INSTRUCTION` 常量 + 自研 `SkillInstructionMiddleware` 告诉模型「先 list_skills 再 load_skill」 | 框架自带技能发现提示词，无需手写 | **直接删**，省一处胶水 |

**22 个 SKILL.md 是标准 Agent Skills 格式**（YAML frontmatter `name`/`description` + Markdown 正文），DeepAgents 原生兼容、原样加载。
**唯一适配坑**：项目 SKILL.md 有自定义字段（`version`/`tags`/`when_to_use`/`allowed_tools`/`required_tools`），框架标准只读 `name`/`description`。`allowed_tools`（限制技能可用工具）需在迁移时改成 DeepAgents 的工具过滤或写进正文约束——**这是要动手的点，不是障碍**。

#### 5.4.2 其余能力逐项映射（框架有的优先换）

| 自研能力 | 代码位置 / 规模 | DeepAgents / LangGraph 内置 | 替换程度 | 备注 |
|---|---|---|---|---|
| 上下文压缩 | `agent/compression.py` 89 行（**仅给 wuwei 上游中间件补日志，非自研压缩**） | DeepAgents 自动摘要 + 大工具结果转文件 + 提示词缓存 | **直接删** | 压缩本就是框架的，这 89 行只是可观测性包装 |
| 记忆 L0-L3 | `memory_pipeline.py` 843 + `memory_loadout.py` 151 + `memory_retriever.py` 316（1310 行） | DeepAgents Memory（AGENTS.md 文件式）+ StoreBackend（按 user/agent 命名空间隔离）+ background consolidation（后台整合） | **部分换** | 文件式记忆 + 后台整合可直接用；L0→L3 的**业务蒸馏规则**是差异化资产，可改写成后台整合 agent |
| 子智能体 | `wuwei_patches.py` + `factory.py` + `business_notifications.py` | DeepAgents `task` 工具（同步/异步并行子智能体，运行中可以打断） | **直接换** | 对照 DeepAgents 异步子智能体 |
| 多智能体 PPT | `multi_agent_ppt_service.py` 317 行（Swarm 三 Agent） | LangGraph supervisor / subgraph + DeepAgents subagents | **部分换** | 编排换框架；PPT 领域逻辑（Planner/Designer/Reviewer 提示词）保留 |
| 任务规划 todos | 项目几乎无（仅 `svg_layouts.py` 中出现字样） | DeepAgents `write_todos` 内置 | **白捡** | 框架直接给，无需自研（0.7 起可选，需手动加） |
| 文件读写/glob/grep 工具 | 无独立自研（工具层零散） | DeepAgents 虚拟文件系统 `ls`/`read_file`/`write_file`/`edit_file`/`glob`/`grep` | **白捡** | 后端可插拔：内存/本地/Store/沙箱 |
| shell 执行 / 沙箱 | `sandbox.py` 216 行（正则黑名单，**可绕过**） | DeepAgents shell 工具 + 可插拔沙箱后端（Modal/Daytona/Deno） | **必须换** | 安全底线，见 5.2 |
| MCP | `mcp_service.py` 676 + `mcp_tool_bridge.py` 363 | DeepAgents / `langchain-mcp-adapters` 官方 MCP 支持 | **部分换** | 连接层换框架；**凭据注入 `$CREDENTIAL`/`$INPUT`、自签证书、SSRF 白名单是业务外壳必须留** |
| HITL 审批 | `approval_manager.py` 352 + `LenientHitlMiddleware` | DeepAgents `interrupt_on`（approve/edit/reject/respond） | **状态机换**（见 4.4） | 审批 UI/通知/审计外壳保留 |

#### 5.4.3 三组结论

- **能直接删、换框架内置**：技能加载插件（换 SkillsMiddleware）、技能注入提示词中间件、上下文压缩日志包装、子智能体（换 `task`）、todos（直接用 `write_todos`）、文件工具（直接用虚拟文件系统）。这些删掉净收益，行为等价或更好。
- **需适配层**：记忆（文件式+后台整合用框架，蒸馏规则保留）、多智能体 PPT（编排换 LangGraph，领域提示词保留）、MCP（连接层换框架，凭据注入外壳保留）、技能管理（DB 退化为索引）。
- **必须保留的业务外壳**：技能/memory 的 DB 索引与后台 UI、按 user/agent 的权限隔离、MCP 凭据注入与 SSRF 白名单、SSE 事件契约、用量记账、审批 UI/通知/审计。

> 立场说明：按用户「能用现成就用、哪怕改动大」的要求，本节把「部分换」项也倾向于尽量交给框架；只有**框架确实没有**（管理后台、权限外壳、业务蒸馏规则）或**换成框架会降能力**（自定义 frontmatter 的 allowed_tools）时才保留自研。

## 6. 战线 C：数据层演进（SQLite/MySQL → PostgreSQL）

> 完整评估见 `docs/design/数据库选型评估-MySQL到PostgreSQL.md`。

### 6.1 前提纠正

项目**默认跑 SQLite**（`config.py:77`），pymysql 只是可选依赖。对 MySQL 耦合很浅：字段多用通用 `Text` 存 JSON，只有知识库全文检索用了 MySQL 专有 ngram 分词 + 两处 `LONGTEXT` variant。

### 6.2 结论

**把 PG 定为"生产推荐 + 未来默认"，开发继续 SQLite；现在补 PG 双轨测试与检索路径，但对存量库做物理迁移要等收益拐点（向量上规模 / 需要 JSONB）。**

### 6.3 动作

1. 文档与配置层：PG 写为生产推荐，`DATABASE_URL` 示例补 PG 写法。
2. CI：PG/MySQL 双库 job，28 个迁移脚本全方言幂等验证（与战线 A 的前置基线合并做）。
3. 知识库检索：补 PG 路径（pgvector + tsvector + HNSW + 中文分词），与 LlamaIndex 方案对齐。
4. 向量库：规模小先用现有 / pgvector，上规模再评估 Qdrant。

## 8. 战线 E：后台管理优化

> 基于 2026-11-17 对后台端的只读排查：`api/v1/endpoints/`、`api/deps.py`、`core/roles.py`、services、`AdminDashboard.tsx`、`components/admin/`（admin/ 共 56 个 tsx、约 2 万行）。

### 8.1 现状全景

后台基础不差：**鉴权模型较完善**（`deps.py` 的 `get_current_user → require_admin → require_capability` 链路，约 126 处引用；`roles.py` 五级角色 + 13 项能力；`/auth/me` 下发 capabilities）。管理端共 21 个 tab / 17 个懒加载面板，分 4 组导航：系统总览 / 对话与内容 / 智能体与能力 / 组织与系统。

已有管理端点规模：`llm_providers.py`(23 路由) / `llmops.py`(24) / `knowledge.py`(20) / `external_systems.py`(22) / `permissions.py`(10) / `users.py`(7) / `dashboard.py`(7) / `workflows.py`(10) / `mcp_admin.py`(7) 等。

### 8.2 P0：高收益低风险（建议立即做）

| 问题 | 位置 | 建议 |
|---|---|---|
| **侧栏菜单无权限过滤** | `AdminSidebar.tsx:63` `navGroups` 是常量 | auditor/operator 能看到「用户管理/API Key/AI 提供商/系统设置」全部入口、点了才 403。后端 capabilities 与前端 `hasCapability()`（`authTokenStore.ts:111`）都已备好，**改一处渲染即可** |
| **作品发布审批硬编码角色** | `published_items.py:107-130` | 用 `Depends(get_current_user)` + `if user.role != "admin"`，导致 superadmin 和持 `CAP_GALLERY_MANAGE` 的 operator 被拒 → 统一 `require_capability("gallery:manage")` |
| **角色判定散落不一致** | `quota_service.py:68`、`api_keys.py:17/33/47` | 只豁免 `role == "admin"`，漏掉 superadmin → 改用 `roles.is_admin_like`。这与优化方案 3.1 的"双轨权限漂移"是同一个根因，建议合并处理 |

### 8.3 P1：需排期

- **信息架构**：`api_keys.py` 实为**个人** sk key，却放在「组织与系统 > API Key」并配"平台级"能力语义——缺真正的平台级 Key 管理；MCP 管理藏在「集成管理」第三个 tab；作品发布审批塞在部署页——审批分散在部署/反馈/发布三处，**无统一「审批中心」**。
- **批量操作缺失**：用户/Key/文档/Skill/公告/反馈均无批量（仅 `KnowledgeManagement.tsx:102` 逐个调用的伪批量）；`admin/published-items` 硬编码 `limit=200` 无分页。
- **任务可观测缺位**：`tasks.py` 只有单任务状态查询，后台无队列列表/失败任务/重试入口；`task_queue.py`(26k)/`task_queue_taskiq.py`(11k) 的失败/死信/重试能力未暴露，队列健康只能看日志。
- **用量成本不可运营**：`quota_service.py` 只有环境变量、无 API/UI；`UsagePanel.tsx` 只挂在聊天侧栏（`Sidebar.tsx:313`）；后台无成本/配额/超限用户视图。
- **系统设置覆盖窄**：`settings.py` 仅 LDAP；SMTP 在个人 `email.py`；审计保留期、注册开关、配额等散在 env/代码常量（`audit_service.py:38`），无后台入口。
- **前后端契约靠手写**：前端 service 手写大量 type（dashboard 18 / llmProvider 19 / knowledge 16 / permission 10 个），无 openapi codegen；`api_keys.py` 用裸 `body: dict`。→ 与战线 B/D 的"OpenAPI 生成客户端"合并做。

### 8.4 P2：长期

- 错误提示/加载态/空状态不统一（`AuditLogTab.tsx` 是正面样板，多数面板各有写法）；排序普遍缺失（`users.py:85` 固定 `created_at.desc()`）。建议沉淀统一列表 hook 到 `admin/shared.tsx`。
- 危险操作确认文案不统一；`purge_audit_logs_endpoint`（`permissions.py:491`）仅 `require_admin`，未叠加 `CAP_DANGEROUS`。
- **健康探针过弱**：`health.py:6` 只返回常量 `{"status":"ok"}`，无 DB/Redis/队列/上游连通性检查。

### 8.5 建议补的功能（与战线 D 联动）

1. **Provider 健康检查面板**：复用 `llm_providers.py:400/438` 的连通测试，批量探测延迟/失败率/账号池状态。
2. **用量成本看板 + 配额管理**：基于 `usage_recorder.py`/`AgentUsageEventModel` 出按用户/模型/部门的 token 与成本；给 `quota_service.py` 补 CRUD API 与后台页（含超限用户与一键放行）。→ 数据来自自研 usage_recorder + OTel SDK 埋点，**不依赖外部 Langfuse**。
3. **任务队列运维台**：列表 + 状态过滤 + 失败原因 + 重试/死信 + 队列深度。
4. **统一审批中心**：聚合 website deploy、作品发布、外调审批（`approval_manager.py`/`agent.py:162`）三类待办 + 计数角标。→ 与战线 A 的 HITL 改造联动，审批形态变化后一起做。
5. **系统健康页**：扩展 `/health` 为依赖级探针（DB/Redis/队列/上游），后台展示最近探测与历史。

### 8.6 风险与取舍

- **可快速做**：菜单按能力过滤、published_items 三处换 `require_capability`、quota/api_keys 角色判断改 `is_admin_like`、审计加 `result=error` 快捷筛选——均局部改动、风险低。
- **中等**：统一批量操作与确认组件（13+ 面板，可增量）、系统设置扩配置项。
- **改动大**：任务队列运维台与成本看板（新数据模型/指标口径）、统一审批中心（跨 3 套状态机）、openapi codegen 全量替换（建议新模块先试点，避免大面积类型回归）。
- **必须守住的边界**：审计清理、Key 吊销等危险操作保留 `require_admin` 并叠加 `CAP_DANGEROUS` 二次确认；对话正文权限（`roles.py` 注释）维持，不因排障默认放开。

## 12. 需要拍板的决策清单

1. **战线 A 是否立即启动全量替换**，还是先只做战线 B/D 的低风险改造、观望 DeepAgents Beta 稳定？（建议：立即启动阶段 0-2，HITL 等 Beta 稳定或走 LangGraph 退路）

# AgenticOS 项目逐功能优化方案

> **实施状态（2026-11-25）：优化项已实施**（含 CI 多库矩阵、DeepAgents 迁移、
> 前端 token 化、运维面板等）；本文保留为原始方案档案，当前状态以 `AGENTS.md` 为准。

> 编写日期：2026-11-17。基于当前仓库代码排查 + 2026 年主流实践调研。
> 范围：后端全部服务/端点、前端、基础设施。逐模块现状与优化点见第 3 节。
> 配套文档：`docs/design/数据库选型评估-MySQL到PostgreSQL.md`、`docs/design/wuwei迁移LangChain方案.md`（独立代理编写）。

## 0. 方法与范围

- 排查方式：遍历 `backend/app/`（297 个 py 文件 / 约 9.6 万行）、`backend/tests/`（134 个测试文件）、`frontend/src/`（314 个 ts/tsx 文件），抽样阅读核心文件，结合网上主流 AI 应用/Agent 平台的实践做对标。
- 优化建议分三类：**P0（高收益低风险，建议优先）**、**P1（有价值需排期）**、**P2（长期/可选）**。
- 每个模块给「现状 → 优化点 → 建议」，不做空泛评价。

## 1. 总体判断（结论先行）

项目已经是一个**功能相当完整、工程质量不低**的平台：约 30 个 API 端点模块、60+ 服务、20+ 工具、134 个测试文件，且对 wuwei 的已知缺陷有补丁层和回归测试兜底，Alembic 迁移幂等性也有纪律。这不是一个"需要推倒重来"的项目。

主要矛盾不在"功能缺失"，而在三处：

1. **规模带来的复杂度**：9.6 万行后端 + 200+ 自定义工具/能力，维护成本和认知负担高；wuwei 深度定制（补丁层、SSE 兼容、审批语义）是最大的耦合点（单列迁移方案文档）。
2. **少数横切工程债**：async 路径里混用同步阻塞调用、前端 API 层 27 个手写 service 缺乏统一契约、数据库默认 SQLite 而生产可选 MySQL 导致双方言维护成本。
3. **AI 应用特有风险**：Prompt/工具/MCP/外部系统/文件操作的攻击面，以及检索质量、Token 成本的可观测性。

**优化主线：优先做"横切、低风险、高收益"的工程改进（第 2 节），再按收益逐模块推进（第 3 节）；涉及框架替换（wuwei）和数据库切换的大动作单独评估、绑定具体收益触发，不盲目启动。**

## 2. 横切优化（跨所有模块，优先级最高）

### 2.1 【P0】async 路径里的同步阻塞调用

- **现状**：`backend/app/services/` 下有 15+ 个文件同时出现 `subprocess.run` / `time.sleep` / `requests.` 等同步阻塞调用，例如 `sandbox.py`、`website_deploy_service.py`、`office/runtime.py`、`ppt/latex_render.py`、`workflow/service.py`、`audit_service.py`。其中不少处在 async 函数/请求链路中。
- **风险**：同步阻塞会卡住 uvicorn 的事件循环，导致并发请求排队；构建网站、渲染 PPT、发邮件这类慢操作尤其明显。
- **建议**：
  - 用 `anyio.to_thread.run_sync()` 或 `asyncio.to_thread()` 把阻塞调用挪出事件循环；`subprocess` 用 `asyncio.create_subprocess_exec`。
  - 对慢操作（网站构建、PPT 导出）走已有的 `task_queue_taskiq.py` 后台任务 + 轮询/SSE 通知，不在请求内等待。
  - 加一条 lint 规则或 CI 检查，禁止在 `async def` 里直接调 `subprocess.run` / `time.sleep` / `requests.*`。

### 2.2 【P0】统一 API 客户端契约（前端）

- **现状**：`frontend/src/services/` 有 27 个手写 service 文件，各自拼 URL / 处理错误；只有单一 `apiClient.ts` 基础封装，类型与错误模型不统一；状态管理只有一个 `chatStore.ts`（zustand），其余页面靠组件本地状态。
- **优化点**：
  - 用 OpenAPI（FastAPI 原生产出 schema）生成 TypeScript 客户端（`openapi-typescript` + `openapi-fetch`），替换手写 URL 拼接，类型端到端对齐、接口变更即时暴露。
  - 统一错误模型（后端异常 → 前端 toast/错误页的映射集中到一处），避免每个 service 各写一套。
  - 按领域拆分 zustand store（chat / agent / admin / knowledge），避免未来单 store 膨胀。
- **收益**：前端 314 个文件的接口调用可维护性大幅提升，减少"后端改了字段前端没跟上"的隐性 bug。

### 2.3 【P1】测试与 CI 工程化

- **现状**：134 个测试文件、覆盖良好，但缺少"多数据库矩阵"验证（默认 SQLite，生产 MySQL，两套方言行为可能漂移）。
- **建议**：
  - CI 增加 PostgreSQL / MySQL 双数据库 job（容器化临时实例），确保 28 个迁移脚本在所有方言下幂等通过（现有 `test_alembic.py` 可扩展）。
  - 保留 `--basetemp=/tmp/agenticos-pytest` 沙箱约定；把 ruff + pytest + 前端 `tsc --noEmit` 固化为合并前必过关卡。
  - 为"慢测试"（真实 MCP、网关联网、office 端到端）打标记，默认跳过、按需显式运行。

### 2.4 【P1】可观测性与成本

- **现状**：有 `agent_run_traces` 审计、`agent_*` 用量记账、`audit_service`；但 Prompt/Token 成本、检索质量、工具失败率缺少统一看板。
- **建议**：
  - 用量记账已按 `user_id` 归属，扩展为"按 app / 会话 / 模型"多维度的成本看板（管理员页已有 `dashboard` 基础）。
  - 给知识库检索加质量指标（命中率、rerank 前后对比、无结果率），支撑 RAG 调参（对应 `eval_grader.py`）。
  - 统一结构化日志字段（request_id / user_id / session_id / provider / model），便于排障与审计关联。

### 2.5 【P1】安全基线（AI 应用特有攻击面）

- **现状**：SSRF 防护（内网爬虫、workflow http 节点）、工具审批、子工具审批、审计、掩码凭据等机制已具备，基础不错。
- **建议**（对照第 4 节调研的主流安全清单）：
  - 定期自动扫描：前端 `npm audit`、依赖 CVE、secret 硬编码（sk_/service_role/私钥模式）。
  - Prompt 注入/越权专项测试：恶意用户输入能否绕过工具审批、读到他人会话数据。
  - 出站域名白名单与文件操作沙箱做穿透测试，确认 SDK 改写无法绕过平台门卫。

## 3. 逐功能模块优化

> 基于 2026-11-17 逐模块代码只读排查。每项标注优先级，路径为仓库相对路径。

### 3.1 认证与权限

- **现状**：自写 JWT(HS256) + PBKDF2 20 万次；会话落库可撤销；登录限流走 Redis 原子窗口(内存 fallback)；LDAP 配置存 `system_settings`、OIDC 用 Authlib；API Key `sk-agenticos-` 前缀仅存 sha256。
- **优化点**：
  - **【P0】双轨权限体系漂移**：`core/roles.py` 能力表(user/auditor/operator/admin/superadmin) 与 `permission_service.py` 的 Casbin(仅 admin/user) 定义不一致，且 `enforce_for_user` 硬编码 `user.role=="admin"` 放行，与 superadmin 等新角色脱节 → 统一到单一角色/能力模型，消除硬编码放行。
  - **【P1】Casbin 策略缓存 5s 延迟**：改策略后多实例最长 5s 不一致 → 写接口主动 `invalidate()`，或缩短到 1s。
  - **【P1】JWT 手写实现**：未校验 header.alg、无 jti/refresh token → 换标准库(PyJWT)并加算法白名单、刷新令牌轮换。

### 3.2 Agent 核心与编排

- **现状**：已拆为 `services/agent/` 包(Mixin 组合)，wuwei 3.4.1 为框架；HITL 走 `LenientHitlMiddleware`+`ApprovalManager`(Redis pub/sub 跨 worker + DB 落库，三档 ask/auto/full)。
- **优化点**：
  - **【P0】补丁层 688 行**：`wuwei_patches.py` 补上游网关缺陷(usage 帧被吞/工具调用丢失/流式无重试)，升级回归风险高 → 见独立迁移方案文档，短期固化回归测试、锁定版本。
  - **【P1】隐式全局状态**：多个 contextvar(`_current_session_id`/ext_user_id/data_path) 跨模块传递，兼容层符号被直接 import，循环依赖风险 → 收敛为显式请求上下文对象。
  - **【P2】巨型文件**：`orchestrator.py` 1693 行 / `factory.py` 1012 行，单类职责过载 → 按职责继续拆分。

### 3.3 LLM 提供商与网关

- **现状**：DB 配置提供商 + 企业 Cookie 账号池轮换 + Playwright 自动登录；`llm_gate` 全局并发闸(本地 Semaphore + Redis Lua)；对外 `/v1` 暴露 OpenAI/Anthropic/Responses/Embeddings/Images 多协议。
- **优化点**：
  - **【P1】Cookie+Playwright 链路脆弱**：credentials/auto_login/presets 共 1600+ 行，强依赖上游页面结构 → 把页面解析规则外置为可配置 preset，失败告警可观测。
  - **【P0】并发闸 Redis 故障静默超发**：注释自述"保可用不保精确"，多实例无强隔离 → 增加超发指标 + 告警，关键租户提供本地强隔离选项。
  - **【P1】网关适配补丁与 wuwei 流式耦合**：`adapter.py` 随上游升级需回归 → 纳入迁移方案统一处理。

### 3.4 工具系统

- **现状**：mode→registrar 自动发现，`TOOL_CATALOG` 由真实执行 registrar 生成；MCP 工具命名 `mcp__<server>__<tool>`，平台侧做凭据注入(`$CREDENTIAL`/`$INPUT`)、自签证书、SSRF 网段限制。
- **优化点**：
  - **【P0】沙箱是"轻量"实现，存在逃逸风险**：`sandbox.py` 用正则黑名单 + 路径检查，无容器/cgroup/seccomp 真隔离，`bash -c`/编码可绕过黑名单，执行 untrusted 命令有高危风险 → 用容器或 `bubblewrap`/`nsjail` 做真隔离，或强制白名单命令。
  - **【P1】工具注册双处维护**：`_GLOBAL_TOOL_REGISTRARS` 与 factory 注册点分离，漏登记导致工具列表缺项 → 单一注册源 + 启动自检。
  - **【P2】超大工具文件**：(email 987 / website 852 / ppt 821 行)混杂业务逻辑与工具定义 → 业务下沉 service，工具文件只留入口。

### 3.5 知识库与记忆

- **现状**：BM25(MySQL FULLTEXT ngram / SQLite Python BM25) + 段级向量余弦双路 RRF，score 归一 0~1 + 启发式重排；Casbin + visibility 双重鉴权；进程内语料 LRU(300s/1000 文档)；记忆 L0→L3 分层蒸馏。
- **优化点**：
  - **【P1】重排权重硬编码、无在线评估**：仅 `recall_test.py` 离线 → 接入 `eval_grader` 做在线命中率/无结果率看板，支撑调参。
  - **【P1】SQLite 全量 BM25 受 1000 文档上限**：难扩大规模 → 生产走 PG 检索(见数据库评估文档)，加 tsvector/中文分词。
  - **【P1】记忆调度进程内存态**：`_turn_counts`/`_llm_semaphore` 重启归零、多实例 L2/L3 不可靠 → 关键计数落库或 Redis。
  - **【P2】knowledge 端点 1125 行**：路由层承载编排逻辑 → 下沉 service。

### 3.6 办公与产物（PPT/A2UI/chart/sheet/website）

- **现状**：文档/表格用 Python 进程 + IPC 驱动 Node 侧 Univer，快照存 `IWorkbookData` JSON；PPT 主路径为 Agent 逐页生成 SVG(18 风格) 再导出 .pptx；A2UI 声明式 UI；chart 用 ECharts。
- **优化点**：
  - **【P0】`ppt_pipeline.py` 疑似半成品/死代码**：`_create_artifact_node` 只构造 dict、注释"这里可以调用 PptArtifactService"却未接，`validate` 硬编码页数≥3 与 `ppt_min_slides=1` 冲突；三套 PPT 路径并存 → 收敛到单一路径，删除或补齐死代码。
  - **【P1】办公 `_sessions` 进程内存态**：重启/多实例丢失会话映射 → 会话元数据落 Redis/DB。
  - **【P2】SVG 校验代码 4000+ 行**：维护成本极高 → 规则配置化 + 抽取通用校验器。

### 3.7 工作流与多智能体

- **现状**：引擎 v2 支持 8 类节点(start/llm/knowledge/http/template/condition/human_input/end)、条件分叉+并行+汇聚+无环校验；变量解析受限点路径(无 eval 防注入)；暂停恢复以 DB 为事实源；eval 用 LLM 语义判分。
- **优化点**：
  - **【P1】暂停恢复两套范式并存**：工作流用 DB、审批用 Redis Future，行为不一致 → 统一为 DB 事实源 + Redis 仅做通知。
  - **【P1】节点失败即终止整条流**：无重试/补偿，HTTP 节点超时(60s)无退避 → 加节点级重试策略(指数退避) + 失败补偿/ Continue-on-error 选项。
  - **【P2】不支持循环节点**：有环校验拒绝，复杂流程受限 → 评估引入受限循环(带最大迭代)。

### 3.8 数据与基础设施

- **现状**：SQLAlchemy 2.0 + Alembic(启动自动 stamp/upgrade)；SQLite WAL / MySQL 池分级；Redis 单机/集群/内存 fallback；任务队列已迁 TaskIQ（arq 依赖已从 pyproject 移除，`task_queue.py` 仅剩废弃兼容 shim）；每日 Token 配额；审计走 `AuditLogModel`。
- **优化点**：
  - **【P0】内存 fallback 多实例静默退化**：缓存/限流/任务派发变进程内状态，虽记 warning 但无强提示 → 生产环境禁用内存 fallback 或启动强告警。
  - **【P0】启动自动迁移失败只记日志不阻断**：可能"代码加字段、库没加列"漂移 → 迁移失败应阻断启动(至少生产环境)。
  - **【P2】任务队列废弃 shim 待清理**：实际已迁 TaskIQ（arq 依赖已删），`task_queue.py` 只剩兼容门面（`WorkerSettings`/`close_arq_pool` 均为废弃空壳）；清掉前需回归 4 个 submit 端点。
  - 数据库选型(SQLite/MySQL/PG)单独评估，见配套文档。

### 3.9 前端

- **现状**：React 19 + Vite 6 + TS + react-router(lazy + ErrorBoundary) + react-query(30s) + Zustand 单 store；SSE 用 `@microsoft/fetch-event-source`；apiClient 统一 fetch(超时/401/错误归一)。
- **优化点**：
  - **【P1】`agentService.ts` 1020 行单文件**：承载全部 SSE 解析分发，Options 40+ 字段膨胀，与后端事件协议强耦合 → 按事件类型拆分 handler 模块，Options 用类型分组。
  - **【P1】chatStore 过渡态**：用 `Dispatch<SetStateAction>` 形状模拟 useState 兼容旧 hooks，会话数据与 UI 状态混在一个 store → 拆分领域 store(见 2.2)。
  - **【P1】token 存储抽象不统一**：apiClient 从 `authTokenStore`、agentService 从 `authService` 分别导入 authHeaders → 统一到单一鉴权源。

## 3A. 横向共性技术债（最高优先）

排查中反复出现的三类模式，建议作为专项处理：

1. **平台侧补丁层过深**：`wuwei_patches.py`(688) / `adapter.py` / `mcp_tool_bridge.py` / mcp 自签客户端，说明对 wuwei 3.4.1 耦合极深 → 见独立迁移方案。
2. **"进程内存态 + 注释'可接受'"处理分布式一致性**：contextvar / `_turn_counts` / `_sessions` / Casbin 缓存，多实例部署隐患集中 → 统一盘点，能落库/落 Redis 的都改造。
3. **Redis 内存 fallback 掩盖生产分布式依赖**：多个模块静默退化 → 生产禁用 + 强告警(见 3.8)。

## 3B. 自研能力 → 成熟开源库替换映射

> 2026-11-17 补充。原则：**能换成熟库就换，但只换"通用能力"，不换"业务/定制资产"**。
> 判据：① 该能力是否有久经考验、许可证友好的库；② 自研实现是否有已知缺陷或维护负担；③ 替换是否会破坏现有对外契约（SSE 事件、API 形状、存量数据）。
> 三个条件都满足才建议换。凡是本项目的**差异化资产**（企业 Cookie 网关、账号池、审批语义、用量归属、SSE 事件协议），一律保留自研。

### 3B.1 建议替换（收益明确、风险可控）

| 自研组件 | 现状与问题 | 推荐成熟库 | 许可证 | 迁移成本 / 风险 |
|---|---|---|---|---|
| **手写 JWT** `core/security.py` | 手写 base64+HMAC，未校验 header.alg、无 `jti`/`exp` 标准校验、无 refresh token | **PyJWT**（明确不要用 python-jose，有 CVE 前科） | BSD | 低。签名/载荷格式兼容，加 `algorithms=["HS256"]` 白名单即可；顺带补 refresh token |
| **PBKDF2 密码哈希** `core/security.py` | 手写 pbkdf2 20 万次；OWASP 2025 已把 PBKDF2 降为"FIPS 等场景备选"，首推 Argon2id | **argon2-cffi**（OWASP 首选，零 CVE，活跃）；如需多方案迁移过渡用 **pwdlib** | MIT | 中。存量哈希需"双验过渡"：登录时先验旧 pbkdf2 再无缝升级为 argon2；passlib 已 2020 起停维护，**不要新用** |
| **MemoryRedis** `core/redis.py` | 自研模拟 string/set/zset/hash/list/pubsub，需自己维护语义一致性 | **fakeredis**（redis-py 的 drop-in 替身，支持异步/pubsub/RESP3，生产稳定版） | BSD-3-Clause | 低。仅用于开发/测试 fallback；生产仍应禁用内存 fallback（见 3.8），fakeredis 只提升"假 Redis"的保真度 |

|---|---|---|---|
| **LLM 提供商网关** `services/llm_providers/`(5857 行) + `adapter.py` + `llm_gate.py` | 自研 DB 配置提供商、账号池轮换、多协议 `/v1` 网关、全局并发闸、成本记账 | **不要整体替换**；若要接 LiteLLM，**只能用它的 Python SDK（库）形态，不用 Proxy** | ⚠️ **LiteLLM 是两种东西**（用户 2026-11-17 明确不要外部系统）：① **Python SDK**＝`pip install litellm` 后在进程内 `litellm.completion()`，纯依赖、零部署，只提供统一调用接口/fallback；② **Proxy / AI Gateway**＝独立 HTTP 服务（Docker/CLI），带虚拟 key/预算/成本看板/管理后台——**这是要单独部署的外部系统，本项目不要**。方案此前把"虚拟 key/预算/成本"当成 LiteLLM 自带优势是**误用了 Proxy 能力**：项目的用量归属（user_id）、网关、并发闸已自研，SDK 正好只补"统一调用 100+ provider"这一小块。结论：如需多 provider 统一接口，用 **SDK 库**塞进现有 adapter；Proxy 形态明确排除 |

| **任务队列** `task_queue.py` + `task_queue_taskiq.py` | arq 早已切 TaskIQ、依赖已删，`task_queue.py` 仅剩废弃兼容 shim | **清理废弃 shim**（非"删 arq"，迁移已完成） | 回归 4 个 submit 端点后再删（见 3E） |

### 3B.3 建议保留自研（属于差异化资产或换库无收益）

- **审批/HITL**（`approval_manager.py` + `LenientHitlMiddleware`）：Redis pub/sub 跨 worker + DB 落库 + 三档策略，与业务语义深度绑定，无等价库。
- **用量记账**（`usage_recorder.py`）：按 `user_id` 归属 + 路由标签，是本项目的计费口径，不能被通用网关的"按 key 记账"替代。
- **SSE 事件协议**（15+ 事件）：前端硬契约，任何框架/库替换都必须写适配层（见 wuwei 迁移方案）。
- **MCP 工具桥**（`mcp_tool_bridge.py`）：凭据注入 `$CREDENTIAL`/`$INPUT`、SSRF 白名单、自签证书客户端是定制安全逻辑；底层 MCP SDK 已用官方库。
- **知识库 RAG 主链路**（BM25+向量 RRF+重排）：RRF 融合与 visibility 鉴权是业务规则；只替换其中的"重排器"这一环（见 3B.1），不整体换框架。
- **限流**：逻辑已正确且简单，换库收益小于风险，仅补指标/告警。
- **前端 SSE 解析**：`@microsoft/fetch-event-source` 已是成熟库，无需替换；要优化的是拆分 1020 行的 `agentService.ts`。

### 3B.4 落地优先级

1. ** immediate（低风险高收益）**：JWT→PyJWT、密码哈希→argon2（双验过渡）、MemoryRedis→fakeredis。
2. **next（需小改造）**：重排器接入 FlashRank/bge（接口已预留）、清理任务队列废弃 shim（迁移已完成）、限流补 metrics。
3. **评估后决定**：沙箱分级加固（P0 安全，优先级实际最高，但需基础设施投入）、LiteLLM 作为新 provider 后端 PoC（保留 Cookie 网关）。

> 依赖变更纪律：所有替换先在 `backend/pyproject.toml` 加依赖并锁版本，跑 `ruff check` + 全量 pytest（尤其 `test_security`/`test_auth`/`test_kb_hybrid_retrieval`/`test_wuwei_patches`），确认对外契约不变再合入。

- **Qdrant（榜单事实，但本项目不接）**：独立向量数据库服务，按 3F.0 红线排除（要单独部署运维）。改用本地已装 PG 的 **pgvector 扩展**，不新增系统；规模未到也无需专用向量库。

1. **OpenAPI 生成替换前端 service**（低风险高收益，立刻做）
2. **OTel SDK（纯库）+ RAGAS** 补可观测与评估（写入自己的 DB，沿用现有 traces/evals tab；**不接 Langfuse**），LiteLLM 只取 **SDK 库**形态做 provider 统一（详见 3B.2、3F.0）
3. **FlashRank + SOPS** 补检索质量与安全短板（纯库/本地 CLI）
4. **沙箱隔离单独立项**：用本地 **nsjail**（进程级 jail），**不用 E2B 托管服务**（见 3F.0）

## 3D. 主流 Agent Harness 调研（2026-11-17）

### 3D.1 先分清三个概念

用户问"主流的 harness"。业界这三个词常被混用，先厘清：

| 概念 | 是什么 | 例子 |
|---|---|---|
| **Harness（执行外壳）** | 承载 LLM 跑起来的"脚手架"：工具循环、上下文管理、文件系统、子智能体、规划、hooks、权限、会话恢复 | DeepAgents、Claude Agent SDK、OpenAI Agents SDK |
| **编排框架** | 用图/状态机精确控制多步骤流程 | LangGraph、Microsoft Agent Framework |
| **Agent 平台** | 带 UI 的低代码/可视化搭建平台 | Dify、Coze、Langflow、n8n |

DeepAgents 官方文档明确自称 "opinionated harness on LangGraph"——**本项目选定的 DeepAgents 本身就是主流 harness 之一**，底座 LangGraph 是编排框架。所以这个调研的核心问题其实是：**有没有比 DeepAgents 更成熟、更该选的 harness？**

### 3D.3 关键结论

1. **选型无需推翻**：本项目已选的 DeepAgents 就是主流 harness 之一，且是少数"模型无关 + 可嵌入 + MIT"的选项。真正能替换 wuwei/DeepAgents 层、纯 in-process、许可证干净的，仍是 DeepAgents（+ LangGraph 底座）。Claude Agent SDK **强绑 Claude 账号/模型 + 底层 spawn 本地 CLI**，Codex harness **绑 OpenAI 生态 + Rust 执行体/沙箱**——两者都与本项目"多 LLM 提供商 / 企业 Cookie 网关"的核心资产冲突，**只能借鉴机制，不能当通用运行时接入**。唯一要用户拍板的是接受 DeepAgents 0.7.x 的 Beta 风险（退路：LangGraph `HumanInTheLoopMiddleware` 等 Stable 同源能力）。
2. **最值得抄的三个机制**（都来自 Claude Code / Claude Agent SDK 的成熟实践）：
   - **permission mode + canUseTool 回调**：`default/acceptEdits/plan/bypassPermissions` 分层 + 细粒度 allow/deny 规则 + 升级到人工审批队列。本项目已有三档 ask/auto/full，可对齐这套语义。
   - **hooks 作为确定性策略点**：`PreToolUse/PostToolUse/PermissionRequest/Stop` 挂回调函数执行"禁止/改写危险命令、审计日志、注入上下文、预算熔断"。关键价值：hooks 是**确定性代码**，不依赖模型自觉——正好补本项目"trust the LLM"的安全短板。
   - **session resume（JSONL 落盘）**：session_id 可恢复/分叉，长任务跨 worker 重启存活——本项目 session_storage 可参考其状态持久化契约。
3. **编程助手类产品（Cursor/Cline/Aider 等）不是"组件"**，是成品应用，无法嵌入本项目；它们的价值只是设计参照。
4. **许可证提示**：Claude Agent SDK 的 Python 版 MIT、TypeScript 版是 Anthropic 商业条款；若将来考虑，只碰 Python 版。且 2026-06 起 Agent SDK 用量走独立月度额度，不看交互配额——成本模型要单独算。

### 3D.4 落地建议

- **不引入新 harness**：维持 DeepAgents + LangGraph，避免多套 harness 并存。
- **抄 hooks 机制**：在本项目工具调用前后加确定性钩子（审计、危险命令拦截、预算熔断），这块现有 audit_service/approval 已有雏形，补齐生命周期点位即可。
- **对齐 permission 语义**：把三档 ask/auto/full 映射成业界通用的 default/plan/auto 语义，便于文档与社区对齐。
- **session 持久化契约**：参考 JSONL resume 思路，强化 session_storage 的断点恢复（与剩余自研排查的会话存储项合并）。

## 3F. 方案重量级组件审查：哪些是没必要的（2026-11-17）

前面几节推荐了不少组件，本节反过来审视：**对一个默认 SQLite、单实例为主、249 端点 / 11 页的中等规模项目，哪些是"为换而换"的重量级，该降级或推迟。**

### 3F.0 组件形态红线：只用"库/依赖"，不引入"需单独部署的外部系统"（2026-11-17 用户明确）

**项目硬约束**：可以加 pip/npm 依赖（代码里 import 即用），但**不要需要单独部署、单独运维的外部系统**（Docker 起服务、独立进程、自带数据库/后台）。按此把所有方案组件重新分类：

| 组件 | 形态 | 判定 |
|---|---|---|
| PyJWT / argon2-cffi / fakeredis / FlashRank / slowapi | 纯库（pip import） | ✅ 可用 |
| **LiteLLM Python SDK** | 纯库：`pip install litellm`，进程内 `litellm.completion()` 调 100+ provider | ✅ 可用（零部署） |
| **LiteLLM Proxy / AI Gateway** | 独立 HTTP 服务（Docker/CLI），带虚拟 key/预算/成本看板/管理后台 | ❌ **排除**（要单独部署） |
| **Langfuse 自托管** | 独立服务 + ClickHouse+PG+Redis+对象存储 | ❌ **排除**（外部系统） |
| **Langfuse Cloud** | 外部 SaaS（数据出境） | ❌ 排除（外部依赖 + 数据出境） |
| **Qdrant / Milvus** | 独立向量数据库服务 | ❌ 排除；改用 **pgvector 扩展**（挂在已装的本地 PG 上，不是新系统） |
| **E2B** | 外部托管沙箱服务 | ❌ 排除；改用本地 **nsjail**（进程级 jail，纯本地工具） |
| **browser-use 云端 stealth** | 部分能力依赖 Browser Use Cloud | ⚠️ 只用开源本地部分，云端能力不用 |
| **OpenTelemetry SDK**（不含 collector/后端） | 纯库：代码里埋点写结构化日志/自己的 DB | ✅ 可用（自建 trace 展示沿用现有 `traces`/`evals` tab） |
| **SOPS** | 本地 CLI 工具（加解密配置文件，无常驻服务） | ✅ 可用 |
| **openapi-ts / orval** | 构建期 codegen（CI 里跑，无运行服务） | ✅ 可用 |

**修正要点**：
1. **LiteLLM 之前混用了两种形态**——方案里"虚拟 key/预算/成本看板"全是 **Proxy 专属**，本项目这些能力已自研（用量记账/网关/并发闸），不需要；只取 **SDK 形态**做"统一调用多 provider"。
2. **可观测改为纯库方案**：不接 Langfuse（自托管=外部系统、Cloud=数据出境），用 **OpenTelemetry SDK 埋点 + 写入项目自己的 DB + 沿用现有 traces/evals 前端 tab**；评估仍可用纯库 **RAGAS**。
3. **向量检索**：不新增 Qdrant 服务，用本地 PG 的 **pgvector 扩展**（PG 是本机已装服务，不算新增外部系统）。
4. **沙箱**：不用 E2B 托管服务，用本地 **nsjail**（进程级隔离，纯本地工具）。

> 一句话：**本方案只加"代码里 import 的依赖"，凡是"要另起一个服务、另运维一套存储"的组件一律不引入。**

### 3F.1 明确过重、应降级的

| 组件 | 方案原建议 | 问题 | 降级结论 |
|---|---|---|---|
| **Langfuse（自托管 + Cloud）** | trace/eval 接 Langfuse | 自托管 = ClickHouse+PG+Redis+对象存储四件套（外部系统）；Cloud = 数据出境。两者都违反"不引外部系统"红线 | **不接 Langfuse**。改用 **OpenTelemetry SDK（纯库埋点）写自己的 DB + 沿用现有 traces/evals tab**，评估用纯库 **RAGAS**（见 3F.0） |
| **Firecracker / Kata 微虚拟机** | 沙箱强隔离选项 | 需 KVM、Linux 宿主，与 macOS 开发/轻部署冲突 | 项目 shell **仅用于 npm build**（`website_tools.py`），不是通用 Agent 执行；**nsjail（进程级）足够起步**，微虚拟机只在公网多租户场景再上 |
| **Qdrant / Milvus 独立向量库** | 向量检索后端 | 新增有状态服务；当前数据量远未到需要专用向量库的规模 | **推迟**。先用 PG+pgvector（见数据库评估），或继续现有应用侧余弦；规模未到就上独立向量库是过度设计 |
| **LlamaIndex 全量接管检索** | RAG 检索/索引交给 LlamaIndex | 引入一套新框架 + 存量切片/embedding 格式对齐，成本高 | **分阶段**：先只换重排器（FlashRank，接口已预留）；LlamaIndex 等确认检索质量瓶颈后再引，别一次全量 |

### 3F.2 有价值但要控制范围的

- **LiteLLM（仅 Python SDK）**：`pip install litellm` 库形态，塞进现有 adapter 做"统一调用多 provider"的旁路 PoC，**零部署**；**不整体替换** 5857 行自研网关（企业 Cookie 池/用量归属/SSE 契约换不掉）。**Proxy / AI Gateway 形态明确排除**（要单独部署运维，见 3F.0）。
- **DeepAgents + LangGraph**：这是主线改造，不算过度；但要**只引这一套 harness + 编排**，别同时引入 smolagents/Agno/PydanticAI 等其他 agent 框架（机制抄来即可，不装库）。
- **PG（PostgreSQL）**：方向对，但**不立即迁存量库**；本机已具备开发环境（见数据库评估阶段 0.5），先做双轨测试。PG 是本机已装的服务，不算新增外部系统。

### 3F.3 提醒：避免重复建设

- **Langfuse 和 Phoenix 都不接**：两者功能重叠，且 Phoenix 是 Elastic License 2.0（SaaS 红线）、Langfuse 是外部系统（3F.0 红线）。自建 OTel 埋点 + RAGAS 即可。
- **不要为了"多智能体"上 Swarm**：项目现有 `multi_agent_ppt_service`/`ppt_pipeline` 是实验死代码（见总方案 4.8）；主路径 PPT 是单 Agent，先别为它引入复杂编排。
- **能复用现有基建就别新增**：会话/审批的持久化已有 Redis+DB，trace 看板已有 `traces`/`evals` tab，先用起来再谈换库。

### 3F.4 一句话原则

**按"当前痛点驱动"而非"生态全家桶"引组件，且只引纯库**：先上低风险高收益（openapi codegen、fakeredis、FlashRank、OTel SDK、LiteLLM SDK）；**凡需单独部署/运维的外部系统（Langfuse、Qdrant、E2B、LiteLLM Proxy、ClickHouse 集群、微虚拟机、LlamaIndex 全量服务化）一律不引入**——要么用纯库替代（pgvector/nsjail/OTel SDK），要么等真到瓶颈再说。这是对项目"默认 SQLite、轻量部署、不养外部系统"定位的尊重。

## 3H. 权限角色体系是否主流（2026-11-17 联网调研 + 代码排查）

### 3H.1 结论先行

**架构不落后，问题是实现漂移。** Casbin 嵌入式库 + 能力表 RBAC 在 2026 仍是主流选型之一，没被 OpenFGA/OPA 淘汰。真正的债是"主流架构 + 瑕疵实现"——双轨没对齐。建议：**保留 Casbin，做低风险修正，不迁移引擎**。

### 3H.2 现状：双轨角色模型

| 轨道 | 文件 | 角色 | 定位 |
|---|---|---|---|
| A. 能力表 RBAC | `core/roles.py:95-101` | user/auditor/operator/admin/superadmin 五级 | 平台功能门禁；端点问"能力"不问角色名，13 项能力累积式（含角色层级语义） |

### 3H.3 漂移点（已核实，比预想严重）

| # | 漂移 | 位置 |
|---|---|---|

| 2 | `enforce_for_user` 硬编码 `user.role=="admin"` 放行；superadmin / 持能力 operator 不放行 | `permission_service.py:277-278` |
| 3 | 知识库三处判定走 `explicit_role`，只认 admin → superadmin/operator 拿不到 KB admin | `knowledge/acl.py:125-132`、`deps.py:280,303` |
| 4 | **硬编码 `role=="admin"` 全后端约 63 处**（实测），漏 superadmin 与 operator | `quota_service.py:68`、`api_keys.py:17/33/47`、`published_items.py:109/116/129` 及 website/llmops/memory/feedback/agent_profile/workflows 等 |
| 5 | 前端 `navGroups` 是常量，未按能力过滤菜单；`hasCapability()` 备而不用 | `AdminSidebar.tsx:63-117` |
| 6 | 策略缓存 5s 进程内，多实例有一致性窗口 | `permission_service.py:43,241-243` |
| 7 | `client_capabilities()` 定义了但生产未调用，前端自行重算 | `deps.py:102-111` vs `authTokenStore.ts:98-108` |

> 影响：auditor/operator/superadmin 在部分端点"名义有权限、实际 403"，或相反——RBAC 最典型的角色漂移 Bug。

### 3H.4 2026 主流方案对照

- **模型层**：业界主流是混合——RBAC 做粗粒度 + ABAC/ReBAC 做对象级；OWASP 建议对象级决策用 ABAC/ReBAC 而非纯 RBAC。本项目"角色=能力集合、端点问能力"正命中最佳实践。
- **引擎层**：Casbin（Apache 孵化、进程内、微秒级、零部署）仍是七大主流之一；Zanzibar 风格（OpenFGA 进 CNCF Incubating / SpiceDB）只在"多服务共享 + 十亿级关系对象 + 专职运维"场景才是趋势。**单 FastAPI 服务 + 五级角色 + 少量行级授权，嵌入库足够**。
- **多租户共识**：check permission 而非 role name、服务端每层强制、记录失败鉴权决策、隐藏按钮≠权限检查——本项目的能力表设计方向对，缺的是彻底贯彻。

### 3H.5 优化方案（分档）

**档 A · 低风险修正（强烈建议，1~2 迭代）**
1. **统一双轨**：`permission_service.py:277` 放行改用 `roles.has_capability()`；Casbin 侧角色覆盖五级，或明确边界"Casbin 只做资源行级、功能门禁全走能力表"。
2. **消除硬编码**：约 63 处 `role=="admin"` 统一换 `is_admin_like()` / `has_capability()`；先修 `published_items.py`/`api_keys.py`/`quota_service.py`，再批量扫尾。
3. **前端菜单按能力过滤**：`navGroups` 每项加 `capability` 字段，渲染用 `hasCapability()`（见 3G）。
4. **缓存一致性**：`POLICY_RELOAD_INTERVAL_SECONDS` 改 Redis pub/sub 失效或 ≤1s；多实例写后广播 `invalidate()`。

**档 B · 架构级迁移（本项目不建议）**
- 换 OpenFGA/SpiceDB：需多服务共享授权 + 十亿级对象 + ZedToken 级撤销一致 + 专职团队；TCO 36 月可达 $7万~$23万，投入产出不成立。
- 换 OPA/Cerbos：适合跨 K8s 统一策略 / 策略即代码强诉求；引入 Rego/YAML 学习曲线。
- 仅当未来出现多服务共享授权或超大规模关系图再评估——届时 AuthZEN 1.0（2026-01 OIDF 最终规范）已降低迁移成本。

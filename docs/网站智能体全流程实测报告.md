## 一、结论速览

**能。** 网站智能体具备「自主生成 → 构建 → 预览 → 申请发布 → 管理员审批 → 上线可访问」的完整闭环，
且这条链路本次被完整跑通（不是纸面设计）。

但「**自主**」有一个明确的边界：**生成与构建是自主的，发布不是**——
发布必须经过管理员审批，这是设计上的有意为之（越权上线风险），不是缺陷。

同时实测发现 **3 个真实缺陷**（下文第五节），其中 1 个会让「从历史版本重新发布」直接失败。

## 二、完整流程（实测通过）

```
用户输入需求
   │
   ├─ ① 模式路由：WEBSITE_ROUTER_PROMPT 判断复杂度 → 选 vanilla / vue / react
   │     并强制先 load_skill("website-design-taste")（反 AI 千篇一律设计规则）
   │
   ├─ ② check_website_project()  —— 查项目是否已存在（禁止跳过）
   │
   ├─ ③ copy_template(stack)     —— 复制模板到 data/websites/u{uid}_s{sid}_v{n}
   │     自动生成版本化目录名，并把「当前项目目录」绑定到文件工具上
   │
   ├─ ④ 文件工具改代码          —— write_text_file / replace_text_in_file
   │     路径自动重定向到项目目录（只给相对路径，杜绝写进 AgenticOS 源码树）
   │
   ├─ ⑤ build_website(slug)     —— 沙箱内 npm install --ignore-scripts && npm run build
   │     产出 dist/
   │
   ├─ ⑥ done 事件 → _create_website_artifact
   │     读 dist/index.html，把 JS/CSS 全部内联成单个 preview_html
   │     同时 snapshot_website_version() 存一个可回看的历史版本
   │     → SSE 推 artifact_ready
   │
   ├─ ⑦ 前端预览面板：iframe srcDoc 渲染（DOMPurify + CSP 沙箱）
   │
   ├─ ⑧ deploy_website(slug) 或 前端「部署」按钮
   │     → POST /api/v1/website/deploy → 落库 status=pending + 写审计
   │
   ├─ ⑨ 管理员审批：POST /api/v1/admin/website/deploys/{id}/decision
   │     approved → _execute_deploy：dist/ 拷到 data/nginx-serve/{slug}/
   │     status=deployed, deploy_url=/sites/{slug}/
   │     尝试 nginx -t && nginx -s reload（失败不致命）
   │
   └─ ⑩ 线上访问：/sites/{slug}/ （已部署）、/preview/{slug}/dist/（未部署直看产物）
```

## 四、工程化能力评估

### 已具备（✅）

- **真工程化构建**：Vite 6 + 真实 `package.json` + 真实依赖树，不是「拼 HTML 字符串」
- **三栈可选**：vanilla（原生三件套）/ vue 3（`<script setup>` + `createWebHashHistory`）/ react 18（+ react-router）
- **版本化项目目录**：`u{uid}_s{sid}_v{n}`，同一会话可迭代多版，版本条可回看
- **构建沙箱**：路径不能逃出工作区、危险命令黑名单、敏感环境变量剥离、120s 超时、输出截断
- **前端预览沙箱**：DOMPurify + CSP（`connect-src 'none'`、`frame-src 'none'`、`object-src 'none'`）
  + iframe `sandbox="allow-scripts allow-same-origin"` + `srcDoc`（不用 blob，避开 StrictMode 双调用 revoke 问题）
- **发布有闸门**：申请 → 管理员审批 → 落库状态机（pending/approved/rejected/deployed/failed）
  + 审计留痕（`website.deploy_request` / `website.deploy_decision`）
- **权限隔离**：非管理员只能部署自己的项目（`_assert_can_deploy_project` 解析目录名比对 user_id）
- **路径穿越防护**：slug 必须是单一目录名，挡 `../`

### 尚未具备（⚠️ 是「单页前端工程」，不是「全栈工程」）

- **无后端**：模板只有前端，没有 API 层 / 数据库 / 服务端渲染。用户提「做一个带登录和订单的商城」，
  智能体只能做前端界面，数据无处可存
- **无部署到外部平台**：只发布到本机 nginx 目录，不是 Vercel/Netlify/自有服务器
- **无域名与 HTTPS**：`target_domain` 字段存在但**全程未被使用**（只落库，不解析、不绑定、不签证书）
- **无依赖增量管理**：模板 `package.json` 写死，提示词明令禁止 `npm_install_package`——
  需要新依赖时**只能提示用户手动改**，智能体无法自主加依赖
- **无测试 / CI / lint 环节**：构建只跑 `vite build`，没有单元测试、类型检查、E2E
- **无增量构建**：每次 `build_website` 都跑一次完整 `npm install`，虽然有 node_modules 缓存但仍耗时 1.3s+；
  而**首次**在 120s 沙箱超时边缘（实测冷缓存 53.6s，网络差时必然超时）

## 五、实测发现的 3 个缺陷

### 缺陷 1【中】历史版本的 `project_slug` 不合法，导致「从历史版本发布」必然 400

`artifact_version_service.build_website_version_artifact` 构造：

```python
"project_slug": f"u{session_id}_v{version}",   # → "use2etest_v1"
```

但真实目录名规范是 `^u(\d+)_s(.+)_v(\d+)$`（`app/core/data_path.py:124`）。实测：

```
真实 slug 解析:        (999, 'e2etest', 2)     ✅
版本条给的 slug 解析:  None                     ❌
```

**影响**：前端版本条切到历史版本后（`WebsiteArtifactPanel.tsx` 的 `onSwitchVersion`
把 `loaded.project_slug` 填回 artifact），用户点「部署」→
`POST /api/v1/website/deploy` → `_assert_can_deploy_project` → `_parse_dir_name` 返回 None
→ **HTTP 400「项目标识不合法」**。即历史版本无法发布。

**次生影响**：该 slug 同时被写进前端 `artifact.projectSlug`，预览面板标题也会显示错乱。

### 缺陷 2【中】构建超时只留半截 `node_modules`，后续构建永久失败

沙箱超时是 `-9`（SIGKILL），`npm install` 被杀死时**已下载的 native 二进制文件被截断**：

```
Error: dlopen(.../rollup-darwin-arm64.node, 0x0001):
  segment '__TEXT' content (fileOffset: 0x0 -> 0x1B4000) extends beyond end of file (length: 0x137B98)
```

**影响**：一次超时污染整个项目目录。之后无论重试多少次 `build_website` 都会失败——
因为 `npm install` 会认为包已安装而跳过，实际文件是坏的。**必须人工 `rm -rf node_modules` 才能恢复**。
智能体没有这个工具，无法自救 → 用户只能看到「构建失败」且反复重试无效。

**根因**：超时后没有清理残留，也没有在下次构建前校验 `node_modules` 完整性。

### 缺陷 3【低】部署记录的 `stack` 字段恒为 `"vanilla"`

`website_tools.deploy_website` 里：

```python
parsed = _parse_dir_name(project_slug)   # 解析了但没用
stack = "vanilla"                          # 硬编码
```

**影响**：数据库里所有部署记录的 `stack` 都是 vanilla。react/vue 站点在后台部署管理列表里
显示为「Vanilla」，无法按技术栈筛选。属显示层缺陷，不影响发布本身。

## 六、当前「自主」边界（明确结论）

| 环节 | 是否自主 | 说明 |
| --- | --- | --- |
| 需求理解 → 选技术栈 | ✅ 完全自主 | 路由器 + 设计品味技能驱动 |
| 写代码 | ✅ 完全自主 | 6 个文件工具，路径自动隔离 |
| 构建 | ✅ 完全自主 | `build_website` 沙箱执行 |
| 预览 | ✅ 完全自主 | 产物内联 + 前端沙箱渲染 |
| 申请发布 | ✅ 自主触发 | 工具或前端按钮 |
| **正式上线** | ❌ **需管理员审批** | **设计如此**：无人值守的自动上线是越权风险 |
| **加依赖** | ❌ 需人工 | 提示词明令禁止 `npm_install_package` |
| **建后端** | ❌ 不支持 | 当前只做前端 |
| **绑域名** | ⚠️ 字段存在但未实现 | `target_domain` 全程未消费 |

## 七、如果要继续增强，建议优先级

| 优先级 | 事项 | 理由 |
| --- | --- | --- |
| P0 | 修缺陷 2：超时后清理 `node_modules` + 构建前完整性校验 | 不修则一次网络抖动就让项目永久无法构建，智能体无法自救 |
| P0 | 修缺陷 1：历史版本 slug 按 `u{uid}_s{sid}_v{n}` 构造 | 历史版本发布功能当前 100% 失败 |
| P1 | `build_website` 超时从 120s 提到 300s，并在超时提示里给出「重试前先清 node_modules」 | 冷缓存实测 53.6s，120s 在弱网下必然踩线 |
| P1 | 补 `npm_install_package` 的安全通道（白名单依赖 + 沙箱安装） | 否则「工程化」有硬天花板——不能自主加依赖 |
| P2 | 支持 `target_domain`：Nginx server_name 绑定 + 证书 | 字段已存在，消费逻辑缺失，属于半成品 |
| P2 | 部署记录 stack 用真实值（`_parse_dir_name` 已有解析结果，直接用模板来源） | 显示正确性 |
| P3 | 构建后跑 `vue-tsc` / ESLint，把错误回喂给模型自查 | 「工程化」的关键一环，目前只有 vite build |
| P3 | 后端能力：FastAPI 侧生成 + 挂载到 `/api/{slug}/` | 从「前端工程」升级到「全栈工程」 |
